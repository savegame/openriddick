# Заключение: стратегия рендера GLES3 (2026-07-27)

Ветка `riddick-render`. Источники: исследование трёх суб-агентов + проверка по
исходникам и декомпилу RndrGL. Связанные доки: `Research_BSP2_Texturing.md`,
`Research_LightPass_Report.md`, `HacksAndHooks.md`.

---

## 0. Краткие ответы на поставленные вопросы

1. **«Текстуры грузятся, но на стенах градиенты чёрное→белое»** — текстуры и
   diffuse-проход тут ни при чём. Градиент рисует **depth-fog проход**: он
   идёт ПОСЛЕ diffuse (alpha-blend, ZCompare EQUAL), сэмплит рамп-текстуру
   `SPECIAL_DEPTHFOGTABLE`, а UV для неё должен считать **TexGen
   (`CRC_TEXGENMODE_LINEAR`)**, которого в нашем бэкенде нет. В итоге рамп
   сэмплится по diffuse-UV стены и размазывается по ней градиентом.
   Мгновенная проверка без пересборки: `XR_ZFOG=0`.
2. **«Игра рассчитана на рендер в буфер / один шейдер на все примитивы»** —
   не подтверждается. У движка полноценная генерация программ: вершинные
   генерируются по ключу `CRC_VPFormat` из шаблона `VP.xrg`, фрагментные —
   именованный набор FP20-программ. «Один шейдер на всё» — это свойство
   нашего порта, а не движка. Следствие: разделение UI/3D **эвристиками —
   тупик**; правильный дискриминатор — ключ шейдера.
3. **«Идти ли планомерно к полной реализации GLES3»** — да. Почти все
   текущие артефакты (чёрный BSP, `AMBIENT_FLOOR`, `NO_LIGHT`, fallback на
   DIFFUSE в BSP2, градиенты, отсутствие лайтмап и теней) — следствия одной
   причины: **shader-pipeline движка выключен** (`m_ShaderMode = -1`).
   Латать дальше по симптомам — умножать HACK'и.
4. **Тормоза в 3D** — да, именно конвертация вершин на лету:
   `Geometry_Precache*` в бэкенде — пустые стабы, поэтому на КАЖДЫЙ draw
   КАЖДОГО кадра идёт `VB_Get(BUILD)` + `malloc` + скалярный `VRegFetch`
   по 9 компонент на вершину + `free` + полный re-upload в кольцевой VBO.
   Плюс PVS в уровнях не читается — рисуются все листья.

## 1. Градиенты на стенах — root cause

`WBSP2Model.cpp:1900-1936` (`VB_RenderQueues`) создаёт fog-атрибут:

```
pAFog->Attrib_RasterMode(CRC_RASTERMODE_ALPHABLEND);
pAFog->Attrib_TextureID(0, m_pSceneFog->m_DepthFogTableTextureID);   // ramp
pAFog->Attrib_TexGen(0, CRC_TEXGENMODE_LINEAR, TEXGENCOMP_U|TEXGENCOMP_V);
pAFog->Attrib_TexGenAttr((fp32*)pTexGenAttr);                        // 2 x vec4
pAFog->Attrib_ZCompare(CRC_COMPARE_EQUAL);
```

- `pTexGenAttr[0] = (VFwd*k, -(VFwd·VP)*k - k*FogStart)`, `pTexGenAttr[1] = 0`
  (`:1912-1921`) — то есть **U = dot(vec4(worldPos,1), attr[0])**, V = 0.
  Это линейная глубина по оси взгляда, нормированная в [0..1] между
  FogStart и FogEnd.
- Приоритет прохода `m_BasePriority_Opaque + CXR_VBPRIORITY_DEPTHFOG` (+19,
  `:2494`), diffuse-проход — `CXR_VBPRIORITY_UNIFIED_ZBUFFER` (-20). Значит
  fog рисуется **последним, поверх** уже затекстуренной стены.
- Наш бэкенд `m_TexGen`/`m_lTexGenMode`/`Attrib_TexGenAttr` **не читает
  вообще** (в `MDisplaySDL2.cpp` нет ни одного упоминания TexGen), берёт
  `m_iTexCoordSet[0]` = TEXCOORD0 = diffuse-UV BSP2 → рамп по UV стены.

Почему спрайты/декали/шрифты нормальные: у них texgen не используется, UV
приходят из вершин.

**Правильный фикс (не хак, ~40 строк):** в вершинном шейдере поддержать
`CRC_TEXGENMODE_LINEAR` для канала: пробросить `m_pTexGenAttr` как две
uniform-vec4 + режим текстурного канала; `uv = vec2(dot(vec4(pos,1),A0),
dot(vec4(pos,1),A1))`. Это первый кирпич будущего VP-генератора (см. §3).

**Временная проверка гипотезы:** `XR_ZFOG=0` (`XREngine.cpp:1397` →
`m_bAllowDepthFog` → `CXR_Fog::DepthFogEnable()`), fog-проход не создаётся
вовсе. Если стены станут текстурированными — гипотеза подтверждена.

## 2. Почему у BSP нет ни лайтмап, ни света (напоминание)

`CXR_Shader::PrepareFrame` (`XRShader.cpp:1258-1290`): `ModesAvail`
собирается ТОЛЬКО из FP20/FP14 caps (нужны `CRC_CAPS_FLAGS_FRAGMENTPROGRAM20`
и **≥8 текстурных юнитов и ≥8 texcoord-сетов**). Ветка TEXENVCOMBINE
закомментирована. При наших caps `ModesAvail = 0` → `BitScanBwd32(0) = -1`
(`MMisc.h:397`) → `m_ShaderMode = -1`, и все `switch(m_ShaderMode)` в
`RenderShading` / `RenderShading_LightField` / `RenderShading_LightFieldMapping`
(`XRShader.cpp:1511/1615/1658`) не имеют подходящего case → **вся shading-
очередь — no-op**. Fixed-pipeline путь (`XRShader_TexEnvCombine.cpp`) в этой
версии (Dark Athena) мёртв: старая сигнатура, никто не вызывает.

Итог: единственное, что видно на экране от BSP2 — Z/ambient-препасс, наш
hack-fallback на DIFFUSE и fog-проход поверх.

## 3. Что означает «полная реализация» в терминах этого движка

Движок ждёт от бэкенда ровно то, что делает PS3GCM:

### 3.1 Вершинная сторона — генератор программ по ключу
- Ключ: `CRC_VPFormat` (`Classes/Render/MRenderVPGen.h`, **в репозитории**):
  texgen-режимы по каналам, lighting (кол-во/типы источников), tangents,
  matrix-palette (skinning), fog, color-vertex и пр.
- PS3: AVL-кэш программ по ключу; промах → `CRC_VPGenerator::CreateVP`
  (`MRenderVPGen.cpp:499`) собирает список `#define` (`TEXGEN0_LINEAR`,
  `LIGHTING`, `USENORMAL`, `MWCOMP%d`, ...) и препроцессит **шаблон
  `System/GL/VP.xrg` из данных игры**.
- Для нас: та же схема, но эмиттер — GLSL ES 3.00. Кэш по ключу
  `CRC_VPFormat`. Здесь же закрываются TexGen (см. §1), вертексный свет,
  skinning (`RIDDICK_SKIP_SKINNED` уходит), туман.

### 3.2 Фрагментная сторона — именованные программы
`CRC_ExtAttributes_FragmentProgram20` (`MRender_Classes.h:737`) несёт
**имя программы + хэш + массив `CVec4Dfp32` параметров**. Набор имён
конечен и мал:

- forward-режим `XR_SHADERMODE_FRAGMENTPROGRAM20` (единственный нужный нам):
  `XRShader_FP20_LFM`, `_LF`, `_NDS`, `_NDSP`, `_NDSEATP`
  (`XRShader_FP20.cpp:2-21`) — **5 программ**;
- deferred-варианты (`FP20Def*`, `FP20DefLin*`) — 14 штук, нам НЕ нужны;
- утилитарные, по литералам `SetProgram("...")`: `TexEnvMode01`,
  `TexEnvProj1`, `XRUtil_VL3P0..3_T1`, `XRShader_Decal*`, `XREngine_Final*`,
  `XREngine_Gauss/Histogram/MotionBlur/RadialBlur`,
  `CMWnd_ModTexture_PaintVideo_YUV2RGB`, `WModel_DarklingEffect_FakeSpawn`
  — **22 имени**, из них для играбельного кадра нужно 5-8 (остальное —
  постпроцесс и спецэффекты, включаются позже).

**Ключевой вопрос по данным (нужна проверка пользователя):** PC-ретейл
грузит эти программы ТЕКСТОМ ИЗ ДАННЫХ ИГРЫ. По декомпилу RndrGL:
- `System/GL/ARB_Fragment_Program/<name>.fp` (`RndrGL:85871, 87815`)
- `System/GL/EXT_Shading_Language_100/<name>.fp` (`:64440, 66093`) — **это
  GLSL 1.00**, то есть готовые исходники, почти совместимые с GLSL ES;
- `System/GL/HL_Shading/<name>.fp` (`:66129, 85858`);
- шаблон вершинных программ `System/GL/VP.xrg`.
PS3-бэкенд делает ровно то же: читает `System/GL/ARB_Fragment_Program/%s.fp`
и конвертирует ARB→Cg (`MRenderPS3_FragmentProgram.cpp:546-557`).

> **ЗАДАЧА ПОЛЬЗОВАТЕЛЮ:** посмотреть в установленной игре, есть ли папка
> `System/GL/` и что в ней (`ls -R System/GL | head -50`). Если там лежат
> `EXT_Shading_Language_100/*.fp` — мы получаем ОРИГИНАЛЬНЫЕ GLSL-шейдеры и
> объём работ падает в разы (адаптация GLSL 1.10 → GLSL ES 3.00 + биндинг
> параметров). Если только ARB-ассемблер — пишем транслятор ARB FP→GLSL
> (механическая работа, ~1-1.5k строк) либо руками 5-8 программ.

### 3.3 Caps
Чтобы движок включил этот путь, `Caps_Flags` должен отдавать
`CRC_CAPS_FLAGS_FRAGMENTPROGRAM20`, а `CRC_GLOBALVAR_NUMTEXTURES` и
`CRC_GLOBALVAR_NUMTEXTURECOORDS` — **≥8** (GLES3 гарантирует 16 texture
units и 16 vertex attribs, так что это честно). Включать — только когда
пункты 3.1/3.2 хотя бы частично готовы, иначе экран станет пустым:
движок перестанет ходить в наш fallback.

### 3.4 Оценка объёма
| Компонент | Оценка |
|---|---|
| TexGen LINEAR/TEXCOORD (минимум для fog) | ~40 строк |
| GLSL-эмиттер вершинных программ по `CRC_VPFormat` (texgen все режимы, свет, skinning) | 1.5-2.5k строк |
| FP20: 5 forward-программ вручную ИЛИ транслятор ARB→GLSL | 0.6k / 1.5k строк |
| Плюминг ext-attrib параметров (vec4-массив → uniform-блок) | ~200 строк |
| Кэш программ по ключу (VP-формат + FP-хэш) | ~300 строк |
| 8 текстурных юнитов + TexEnvMode + текстурные матрицы | ~400 строк |

Итого «настоящий» рендер — порядка 3-5k строк, что на порядок меньше
исходной оценки 10-20k в CLAUDE.md, потому что вся вариативность уже
описана движком (формат ключа и имена программ), а не изобретается нами.

## 4. Разделение UI и 3D

Текущая схема (хинт `Render_SetUIPass` + эвристики `IsUI2DDraw`) — попытка
угадать намерение движка по состоянию. Она принципиально хрупкая: UI, HUD,
консоль, загрузочные экраны, видео и отложенные VBM-флаши идут разными
путями, а часть 3D-геометрии выглядит как 2D (identity-модель, ZWrite off).

### 4.1 Точка, которая закрывает вопрос хинта раз и навсегда

Весь 2D-контент движка идёт через ОДИН класс — `CRC_Util2D`
(`Classes/Win/MWinGrph.h:27`, реализация `MWinGrph.cpp`). Проверенные
точки входа:

| Путь | Где | Покрыт хинтом сейчас |
|---|---|---|
| Фронтенд/меню | `WFrontEnd.cpp:346-431` (`Util2D.Begin` :354, `RenderTree` :394) | да |
| **In-game HUD** | `WClientMod.cpp:795, 847-853, 876-884, 1015, 1041` — свой член `m_Util2D` | **нет** |
| **Видео/фейды** | `MWinMovieController.cpp:203/265/320` — временный `CRC_Util2D TempUtil` (:247, :302) | **нет** |
| Загрузочные экраны | обычные `CMWnd` в дереве фронтенда | да |
| Консоль | `MConsole.cpp:1626` — легаси CPU-блиттер через `CImage*`, не через VBM | вне вопроса |

**Вывод: хинт надо ставить не по call-site'ам, а один раз внутри
`CRC_Util2D::Begin()` / `End()` (`MWinGrph.cpp:119` и парная).** Это
единственная точка, через которую проходит весь 2D без исключений, и она
делает эвристики `IsUI2DDraw`/`Is2DProjection` ненужными немедленно —
ещё до кэша программ.

Про «родной» дискриминатор: `CXR_VBPRIORITY_WINDOWS = 10000` /
`CXR_VBPRIORITY_CURSOR = 10100` (`XRVBPrior.h:35-36`) зарезервированы под
UI, но `CRC_Util2D::SetPriorityValues` по умолчанию ставит базу 0
(`MWinGrph.cpp:42-51`), а бэкенд `m_Priority` вообще не читает. Т.е. как
маркер он не работает без доработки с обеих сторон — `Util2D::Begin` проще.
`CXR_ViewClipInterface` (`XRClass.h:1085`) к UI отношения не имеет (это
отсечение порталов/зеркал для 3D).

Правильная модель — **не два шейдера, а кэш программ по ключу**:
ключ = (`CRC_VPFormat`-подобная выжимка из атрибутов) + (имя/хэш FP-программы
из `m_pExtAttrib`) + флаги (fog/alpha-test/texenv). UI при этом
автоматически превращается в вариант вроде `TexEnvMode01` — тот самый
именованный FP, который движок и просит для 2D-путей. Никаких эвристик и
никакого «какого класса этот draw».

Практический вывод: хинт `Render_SetUIPass` оставить (дёшево, полезен для
FBO-композиции UI отдельным слоем — Фаза 5), а эвристики `IsUI2DDraw` —
кандидат на удаление сразу после ввода кэша программ. Отдельные FBO для UI
и 3D — это вопрос **композиции**, а не шейдеров, и он ортогонален: делать
после того, как кадр станет правильным.

## 5. Производительность

Подтверждено по коду:

1. `Geometry_PrecacheFlush/Begin/End/Precache` в `CRC_GLES3` — **пустые
   стабы** (`MDisplaySDL2.cpp:3445-3448`), хотя движок реально их вызывает
   при загрузке уровня (`WClient_Precache.cpp:937`, `WFrontEndMod.cpp:668`).
2. Поэтому `Render_VertexBuffer` (`:3336`) и
   `Render_VertexBuffer_IndexBufferTriangles` (`:3386`) на каждый draw
   каждого кадра: `VB_Get(BUILD)` → `BuildVertsFromVBB` (`:3168`) →
   `malloc(48 байт × nV)` (`:3276`) → до 9 скалярных `VRegFetch` на вершину
   (`:3107-3157`) → `free` (`:3372, 3439`) → полный re-upload в кольцевой
   VBO (`GLES3_VBOStreamer.cpp:45-82`, при переполнении — orphan).
   И это для **статичной геометрии уровня**, которая не меняется вообще.
3. Эталон PS3GCM: `m_lpVB[VBID]` + бит `m_Fresh`,
   `Geometry_Precache(VBID)` → `Build(VBID)` один раз с последующим
   `VB_Release(VBID)`; draw = `Bind(VBID)` + `gcmSetDrawIndexArray`
   (`MRenderPS3_Geometry.cpp:1102-1145`, `MRenderPS3_Render.cpp:220-267`).
   Инвалидация — `Destroy(VBID)` / `PrecacheFlush` / `PostDefrag`.
4. PVS: если чанк отсутствует — `WBSP2Loader.cpp:2557-2567` «ALL LEAVES
   VISIBLE», рисуются все листья уровня. Умножает пункт 2.
5. Мелочи: DXT декодируется на CPU в RGBA8 (`GLES3_DXT.cpp`), аппаратного
   `glCompressedTexImage2D` нет вообще — ×4-×8 памяти и время загрузки.

План: (а) VBO-кэш по VBID с реализацией `Geometry_Precache*` — даёт
основной выигрыш; (б) разобраться с PVS; (в) батчинг; (г) S3TC на GPU.

## 6. «Стартовать без эффектов по умолчанию»

Найденные рычаги (движковые, через registry/env, без пересборки):
- `XR_ZFOG=0` — depth-fog проход (см. §1);
- `XR_DLIGHT=0` — динамические источники;
- `XR_STENCILSHADOWS=0` — стенсильные тени (осторожно: в BSP2 без них свет
  течёт сквозь стены);
- `XR_WALLMARKS=0`, `XR_FLARES=0`, `XR_WORLDONLY=1` — декали, флары, только мир;
- `RIDDICK_DIRECT_RENDER=1` — наш флаг: рендер в fb0, `Engine_PostProcess`
  гейтится (`XREngine.cpp:4405+`, ранний `return` по `sDirectRender`),
  CamFX отключается.

Плюс движковые флаги отладки постпроцесса, которые можно выставлять
напрямую: `CXR_Engine_PostProcessParams::m_DebugFlags`
(`XREngine.h:69-76`): `XR_PPDEBUGFLAGS_NOGLOW`, `NOFINAL`, `NOGAUSS_X/Y`,
`NOOVERRIDE` — гейтят glow/blur/composite внутри `Engine_PostProcess`
(`XREngine.cpp:4475-4479`); `m_PostProcess_MBDebugFlags` (:1248, :4491) —
motion blur; `VIDEO_CHARSHADOWS` (`XRApp.cpp:6079`) — тени персонажей;
`m_CamFXMode`/`DARKNESSVISION` (`WClientMod.cpp:104, 461-562`) — camera-fx.

Про сглаживание — **гипотеза не подтвердилась на уровне кода**: в этом
снапшоте `r_antialias` зарегистрирован как `DummyInt`/`Cmd_Nop`
(`XRApp.cpp:6865`, `MRenderPS3_Cmd.cpp:91`), реализации MSAA-девайса в
дереве нет вообще, а `CRC_RENDEROPTION_NOANTIALIAS`
(`MRender_Classes.h:28`) используется только в закомментированном блоке
(`WClientMod_DV.cpp:951`). Опция игры (`OPTG\VIDEO_DISPLAY_ANTIALIAS`,
`WFrontEndMod_Menus.cpp:1514, 1582`, env `R_ANTIALIAS`, `XRApp.cpp:6244`)
хранится, но в этом коде ни на что не влияет. Скорее всего в PC-ретейле
MSAA включался на уровне GL-девайса в RndrGL, и постпроцесс отключался
из-за невозможности дешёвой капчи MSAA-бэкбуфера как текстуры, — но
**«зачатков direct render» в исходниках это не даёт**. Полезный вывод
другой: путь без RTT-капчи всё равно легитимен, у нас он уже есть
(`RIDDICK_DIRECT_RENDER`), и он именно так и должен быть режимом
композиции, а не источником правды о шейдерах.

Что ломается под `RIDDICK_DIRECT_RENDER=1` (для понимания цены): env-map
и mirror-капчи, пирамиды downsample для glow/blur, экспозиция/гистограмма,
финальный composite-квад (`XREngine.cpp:4407-4419`) и полноэкранные
camera-fx квады (`WClientMod.cpp:449-458`). Меню Dark Athena RTT-интенсивно
штатно: `WFrontEndMod_Cube.cpp` делает `AddCopyToTexture` на 6 граней куба
(:3452, :3774, :4463) + blur/glow-пирамиды и композит (:3526, :3634,
:3715, :4101, :4510, :5263, :6179, :6289, :6367) — отсюда те ~20-30 копий
на кадр.

## 6a. Управляемое качество рендера (требование, 2026-07-27)

Требование пользователя: порт должен давать **более гибкую настройку рендера,
чем оригинал** — вплоть до отключения целых механизмов ради слабых устройств
(ARM-таргет — одна из целей проекта, см. Фазу 6 в `CLAUDE.md`).

Конкретные режимы, которые надо уметь включать/выключать независимо:

| Переключатель | Что делает | Что даёт |
|---|---|---|
| lightmaps only | рисуем только запечённый свет (`XRShader_FP20_LFM`), все динамические проходы (`NDS`/`NDSP`) не исполняются | самый дешёвый режим: 1 проход на поверхность вместо N+1 по числу источников. Требует, чтобы LFM был починен (тангенты) |
| dynamic only | текущее поведение оригинала: свет только от источников | эталон, «как в игре» |
| per-pixel lighting off | нормал-мапа не сэмплится, освещение по вершинной нормали | убирает выборку текстуры и тангентный базис из горячего пути |
| specular off | спекулярный член не считается | дешевле, визуально малозаметно на матовых поверхностях |
| projective maps off | конус фонарика без маски | экономит текстурный юнит и выборку |
| shadow volumes off | стенсильные тени не строятся | заметная экономия CPU (силуэты строятся каждый кадр) и fill-rate |

Архитектурные следствия, которые надо держать в голове **уже сейчас**:

1. Эти переключатели — не `#ifdef`, а **runtime-состояние**: они должны входить
   в ключ выбора программы (см. §4), иначе получим комбинаторный взрыв
   статических шейдеров. То есть когда дойдём до кэша программ по ключу, ключ
   обязан включать биты качества, а не только `CRC_VPFormat` + имя FP-программы.
2. «Lightmaps only» реализуется не в шейдере, а **отбрасыванием проходов**:
   draw'ы с ext-attrib `XRShader_FP20_NDS/_NDSP` просто не исполняются. Место
   для фильтра — там же, где сейчас живёт `DrawIndexed_ShouldSkip`.
3. Пока флаги живут как env-переменные (`RIDDICK_LFM`, `RIDDICK_NDS`, ...), но
   правильное место для них — движковый реестр настроек, рядом с
   `VIDEO_*`-ключами (`XRApp.cpp:6067+`), чтобы это стало пунктами меню
   графики, а не переменными окружения.

Не делать сейчас — сделать, когда появится кэш программ по ключу (R3) и
заработают LFM+NDS. Но проектировать эти два шага надо с оглядкой на таблицу
выше.

## 7. Рекомендуемый порядок работ

Принцип: каждый шаг оставляет картинку на экране не хуже предыдущей.

- **R0. Производительность (независимо от всего).** VBO-кэш по VBID +
  реализация `Geometry_Precache*`. Не трогает визуал, снимает главный
  тормоз, дальше отлаживаться будет комфортно.
- **R1. TexGen.** `CRC_TEXGENMODE_TEXCOORD` + `LINEAR` в вершинном шейдере.
  Чинит градиенты на стенах (fog станет настоящим). Проверка — `XR_ZFOG=0/1`.
- **R2. Разведка данных.** Проверить `System/GL/` в установленной игре
  (§3.2). От результата зависит R3.
- **R2b. Хинт UI в `CRC_Util2D::Begin/End`.** Переставить
  `Render_SetUIPass` из `WFrontEnd::OnRender` внутрь `CRC_Util2D`
  (`MWinGrph.cpp:119`), удалить эвристики `IsUI2DDraw`/`Is2DProjection`.
  Закрывает HUD и видео-фейды, которые сейчас классифицируются наугад.
  Дёшево и независимо от остального.
- **R3. Кэш программ по ключу.** Ввести ключ шейдера (VP-формат + FP-имя),
  переехать на него; UI/3D-эвристики удаляются. Пока FP-программ нет — все
  ключи мапятся на текущие два шейдера, регрессии нет.
- **R4. Вершинный генератор.** Все texgen-режимы, вертексный свет,
  skinning. Снимает `RIDDICK_SKIP_SKINNED`, оживляет проективные лайты.
- **R5. FP20 forward.** 5 программ (`_LFM` — лайтмапы BSP2, `_NDS/_NDSP` —
  дифуз+нормаль+спекуляр от источника). Включить caps FP20 + 8 юнитов.
  Здесь мир получает лайтмапы и динамический свет; уходят hack-fallback в
  `WBSP2Model.cpp`, `AMBIENT_FLOOR`, `NO_LIGHT`, `FORCE_TEX`.
- **R6. Тени и остальное.** Стенсильные объёмы (стейт уже корректный),
  user clip planes для порталов/зеркал, VB-операторы (fresnel, env).
- **R7. Постпроцесс и раздельные FBO UI/3D.** Только после R5 — иначе
  композитим неправильную картинку.

Порядок R0→R1 даёт быстрый видимый результат (стены с текстурами и
приемлемый FPS), R3-R5 — «настоящий» рендер.
