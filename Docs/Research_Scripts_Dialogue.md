## 1. Наблюдения (уровень `diner`, столовая)

* NPC **разговаривают, звук идёт**, но **рот не открывается**;
* все, кто ходит, **скользят по полу в позе первого кадра ходьбы**;
* **начать диалог с NPC нельзя** ни с одним;

Важное следствие из первого пункта: **звуковая часть диалога работает**.
Значит проигрывание реплики (SFX/поток) идёт своим путём, а ломается то, что
должно сопровождать реплику — лицевая анимация и, судя по остальному,
состояния анимграфа.

## 3. Зацепка из декомпайла ретейла (GameWorld DLL)

Грепом по `GameWorld_Win32_x86_dll_decomp.c`:

| Строка | Что там |
|---|---|
| `:103125` | `"Dialogues/All.xcd"` — тот самый общий контейнер |
| `:95143` | `"Dialogues/%s.XCD"` — **пофайловый фолбэк по имени диалога** |
| `:95420` | `"DIALOGUES/"` — префикс, по которому имя ищется внутри контейнера |

Ключевое — `:95143`. Ретейл, **не найдя запись в контейнере**, строит путь
`Dialogues/<имя>.XCD` и проверяет его через `CDiskUtil::FileExists`. То есть
дисковый фолбэк в ретейле ЕСТЬ (в наших заметках раньше было записано
обратное — это надо перепроверить и поправить).

Отсюда две проверяемые версии:

1. **контейнер не тот/не открывается** — `All.xcd` в PC-наборе может лежать
   не в `Content\Dialogues\`, а в архиве (XDF) или под другим регистром;
   наш `[DLG] exists=0` говорит именно об этом;
2. **мы не делаем фолбэк**, который делает ретейл: одиночные `Dialogues/
   <имя>.XCD`. Проверить, есть ли такие файлы в наборе; если есть — путь
   починится тривиально.

Дополнительно: `CMFileContainer::GetEntry` — **бинарный поиск** по списку
записей, а `Create()` читает их в порядке файла и не сортирует. Если
контейнер всё-таки открывается, но записи не отсортированы, поиск будет
промахиваться на существующих именах. Это отдельная проверка (сравнить
порядок имён в контейнере с лексикографическим).

## 4. Про «рот не открывается»

Лицевая анимация в этом движке — отдельная подсистема (`WDataRes_FacialSetup`,
морфы/FaceFX). В нашей сборке FaceFX-обёртки **исключены из сборки** (см.
`CLAUDE.md`, Фаза 2: «исключены Win32/Xenon/PS3-TU, ASIO, FaceFX/Bink/XMV»).
Поэтому «звук есть, рот молчит» — ожидаемое поведение текущей конфигурации,
а не загадка. Отдельная задача: понять, что именно в PC-контенте отвечает за
липсинк (данные FaceFX или морф-таргеты в модели) и можно ли поднять это без
проприетарной библиотеки.

## 5. План проверок (по одной, с логом)

1. **Есть ли файлы диалогов на диске.** Просто посмотреть набор:
   `Content/Dialogues/` — есть ли `All.xcd` и/или одиночные `*.XCD`, и
   в каком регистре. Это отвечает сразу на §3.1 и §3.2 без кода.
2. **Зонд на открытие контейнера**: путь, который реально строится, результат
   `FileExists`, число записей после `Create()`, и первые 5 имён — чтобы
   увидеть и промах пути, и несортированность.
3. **Фолбэк как в ретейле**: если одиночные `.XCD` есть — добавить путь
   `Dialogues/<имя>.XCD` (ровно как `:95143`).
4. **AG2-слои** (общая с костями задача): какие слои возвращает
   `Char_GetAnimLayers` для NPC в столовой, идёт ли время слоя, меняется ли
   состояние. «Первый кадр и скольжение» = состояние вошло, а время/переход
   не идут.
5. **`Sequence -5`**: найти, кто кладёт отрицательный индекс
   (`CWObject_Engine_Path`), — спецзначение или последствие несчитанных
   данных.

## 6. Образ PS3-диска — что с него полезно

Пользователь распаковал образ PS3. Полезно будет (по убыванию):

* **дерево `Dialogues/`** — состав и имена (`All.xcd` против одиночных
  `*.XCD`), это прямо закрывает §3;
* **дерево `AnimGraphs`/`*.AG2`/анимации персонажей** — сверить версии и
  состав с PC-набором (у нас уже была разница AG2 v6);
* **шейдеры/VP-программы PS3** (`*.xrg`, VP-шаблоны) — как справочник для
  FP20/NDS-программ бэкенда;
* общий список файлов верхнего уровня — чтобы понимать, какие подсистемы в
  PS3-сборке отдельными файлами (FaceFX-данные, локализация).

**Важно:** PS3-ресурсы big-endian и форматы местами отличаются от PC.
Их роль здесь — **справочник для сверки форматов**, а не замена PC-контента.
Гонять игру предполагается на PC-наборе.

## 7. РЕШАЮЩАЯ НАХОДКА (2026-08-03, списки файлов PC и PS3)

Списки положены в репозиторий: `Docs/ResourceLists/pc_files.txt` (4911 строк)
и `Docs/ResourceLists/ps3_files.txt` (809).

```
PC :  ./Content/Dialogues/Dlg_JohnDoe.xrg
      ./Content/Dialogues/PA2/Pa2_Diner/Dlg_Barrasa.xrg      <-- ПОДПАПКИ
      ./Content/Dialogues/PA2/Pa2_Diner/Dlg_Shivers.xrg
      (691 записи, файла All.xcd НЕТ вообще)
PS3:  ./PS3_GAME/USRDIR/CONTENT/DIALOGUES/ALL.XCD            (и по языкам)
```

Три вывода:

1. **`All.xcd` — это PS3-упаковка.** На PC его нет и быть не должно, значит
   `[DLG] container exists=0 entries=0` — норма, а не дефект. Гоняться за
   контейнером не нужно.
2. **Цепочка фолбэков в коде УЖЕ ретейловая**: `WDataRes_Sound.cpp:698`
   пробует `DIALOGUES\<Name>.XCD`, затем `:706` — `DIALOGUES\<Name>.XRG`.
   То есть отдельный фолбэк добавлять не надо, он есть.
3. **Ломается на подпапках.** Код строит ПЛОСКИЙ путь
   `DIALOGUES\<Name>.XRG`, а PC-контент раскладывает диалоги по уровням:
   `Dialogues/PA2/Pa2_Diner/Dlg_Barrasa.xrg`. Для всего, что лежит глубже
   первого уровня, `FileExists` закономерно даёт false — отсюда и «диалог не
   начинается» в столовой (`Pa2_Diner`).

Заодно: `Dlg_Player_Base` в PC-наборе **отсутствует вовсе** (0 совпадений в
списке), так что вечный `WARNING: Dialogue ...\Dlg_Player_Base.XRG does not
exist` — безвредный шум, а не след.

### Что править (точка одна)

`WDataRes_Sound.cpp`, около `:698-712`. Нужен поиск по подпапкам
`Content/Dialogues/**`, а не только плоский путь. Варианты:

* однократно просканировать `Dialogues/` рекурсивно (движковый файл-поиск уже
  есть — `PS3File_Find*` в `MRTC_System_Linux.cpp`) и построить карту
  `имя -> путь` (регистронезависимо), фолбэк смотрит в неё;
* либо, если имя диалога где-то рядом несёт префикс уровня, — подставлять
  `DIALOGUES\<уровень>\<Name>.XRG`. Проверить по вызывающему коду, что
  приходит в `Name` для NPC из столовой.

Первый вариант надёжнее: он не зависит от того, как контент разложен по
кампаниям (в списке есть и `Dialogues/TEST/`, и `Dialogues/PA2/...`).

## 8. Уточнение симптомов анимации (2026-08-03)

* **Статические анимации работают**: персонаж стоит и курит, двое
  разговаривают и жестикулируют — всё играет.
* **Активные действия замирают**: переход к бегу/атаке — анимация встаёт.
* **NPC не атакуют**: бегают за игроком, но не стреляют.

Это сильно сужает поиск: работают состояния, в которые персонаж УЖЕ вошёл и
которые лупятся; ломаются ПЕРЕХОДЫ и действия. То есть подозрение не на
проигрывание анимации, а на граф состояний AG2: переход не выполняется
(MOVETOKEN/GRAPHBLOCK не найден, guard'ы из `WAG2I_Resources.cpp` глотают
спецзначения) либо действие не доходит до анимграфа.

Прямая связь с «не стреляют»: выстрел в этом движке идёт через состояние
анимграфа (анимация атаки → событие → выстрел). Если переход не выполняется,
не будет ни анимации, ни выстрела — ровно то, что видно.

Следующий зонд: в `MoveGraphBlock`/`GetMatchingGraphBlock` печатать
запрошенный MOVETOKEN, найденный блок и причину отказа. У нас там уже стоят
guard'ы с `ConOut`, но они молчаливо возвращают — надо, чтобы называли токен.

### 9.1 Диалоги ЗАГРУЖАЮТСЯ. Гипотеза §7.3 неверна

Зонд `[DLG] name=` (`WDataRes_Sound.cpp`) отдал 30 имён, и имена **несут
подпуть**:

```
[DLG] name='PA2/Pa2_Diner/Dlg_Georgie'
[DLG] name='PA2/PA2_Diner/Dlg_Riddick'
[DLG] name='Dlg_Default_Guard4'
```

Предупреждений `WARNING: Dialogue ... does not exist` при этом ровно **9 на
30 запросов**, и ни одного — на дайнерские диалоги. То есть плоский путь
`DIALOGUES\<Name>.XRG` работает: `Name` уже содержит `PA2/Pa2_Diner/`,
а прямые слэши и разнобой регистра (`PA2/PA2_Diner` в запросе против
`Dialogues/PA2/Pa2_Diner` на диске) снимает `Linux_ResolvePath`
(`MRTC_System_Linux.cpp`) — регистронезависимое разрешение плюс `\`→`/`.

**Вывод: рекурсивный скан `Content/Dialogues/**` не нужен, править
`WDataRes_Sound.cpp:698` не нужно.** Пункт §7.3 отменён.

Что действительно не нашлось (сверено с `Docs/ResourceLists/pc_files.txt`):

| Имя | В PC-наборе | Комментарий |
|---|---|---|
| `Dlg_Player_Base` | нет | 0 совпадений; шум, как и записано в §7 |
| `PA2/Pa2_T17/Dlg_Lightguard` | нет | `Dlg_Lightguard.xrg` есть только в `PA2/Pa2_M_Rift/` |
| `Dlg_Default_RGuard4` | нет | на диске `Dlg_Default_Guard_RGuard4.xrg` |

Первые два — дыры контента, ретейл ругался бы так же. Третий любопытен:
имя приходит из родительской цепочки (`Name = spReg->GetValue(0)` в цикле
`while(Name != "")`), и файл с похожим именем существует. Проверять стоит
не путь, а то, что лежит в `*DIALOGUE` внутри `Dlg_Default_Guard4.xrg`.
Приоритет низкий: это один гвардейский фолбэк, не причина «диалог не
начинается ни с кем».

### 9.2 Анимграф ПЕРЕХОДЫ ЗАПРАШИВАЕТ и не отказывает

`[AG2] req` — 400 строк (упёрлось в кап), токены 0/6/7/8/9, движущиеся
MOVETOKEN'ы (113, 116, 121, 1354, 1783, 2867, 3057, 3207, 3249…).
И при этом **ноль** строк `AnimGraph BROKEN` и **ноль** `INVALID MOVETOKEN`.

Значит закрыты сразу две версии из §8: до анимграфа игровая логика доходит,
и известные guard'ы в `MoveGraphBlock` ничего не глотают. Искать надо
дальше по цепочке — во входе в состояние и в проигрывании анимации слоя, а
не в маршрутизации графа.

### 9.3 Настоящая причина «реплика не идёт»: нулевая длина сэмпла

В логе:

```
MOTORHEAD failed Dialogue: SUSPICIOUS_SOUND Dialogueindex 246
MOTORHEAD failed Dialogue: COMBAT_SPOTTED  Dialogueindex 600
```

Это `AI_DeviceHandler.cpp:1375` — печатается, когда
`CWObject_Character::GetDialogueLength()` вернул **0**. Дальше по коду:
`GetDialogueLength` → `GetSampleLength_Hash` → `GetSampleLengthBuf`
(`WDataRes_Sound.cpp:1984`), а тот отдаёт ноль, если у реплики нет
привязанного звука **или** `CWRes_Sound::GetSound()` вернул NULL, и при этом
среди событий нет ни одного тайминга субтитра.

Рядом в логе — вал `WARNING: Undefined sound: SND:D_PA2_Riddick_145`,
`SND:D_PA2_Abbott_100..102`, `SND:D_Base_Guard4_347..352`,
`SND:D_PA1_Mattsson_107` и т. п. Это `CWRes_Sound::OnLoad`
(`WDataRes_Sound.cpp:170`): имя не нашлось ни в одном контейнере волн,
`m_iSFX` остался −1, а значит `GetSound()` = NULL. Круг замыкается.

Откуда берутся дескрипторы: PC-контейнеры волн **не содержат бинарной
секции SFXDESC**, дескрипторы лежат текстом в `Content/SfxDesc/*.xsfxc`, и
разбирает их **наш собственный парсер** — `NSFXDescScript` в
`MSound_SFXDesc.cpp` (порт-хак, ретейл читал это через
`CWaveContext::ReadSfxDesc`). В прогоне: `318 wave containers loaded`,
`23033 sfxdescs loaded (275 files)` — все 275 `.xsfxc` из набора прочитаны,
но часть имён всё равно не резолвится.

Отсюда рабочая версия: **дефект в нашем парсере/сопоставлении шаблонов
`*Source`, а не в контенте.** `BuildDescs` заводит дескриптор только на те
волны, которые нашлись в контейнере по `WildcardMatch`; если шаблон в
`.xsfxc` использует синтаксис, который мы не покрываем (или имя волны в
контейнере хранится хэшем — см. `GetWaveName()` «returns the name hash as a
hex string in this build»), дескриптор не создаётся молча.

Это же объясняет и «звук идёт, но не у всех»: работают те реплики, чьи
дескрипторы собрались.

### 9.4 Отдельный куст: навигация. NPC не доходят до целей

```
(CWorld_ServerCore::World_Init) Using plain pathfinder
Script MOVE_TO_SCENEPOINT request failed: DINERBEATER1 SP_PB1A
DINERBEATER3: AlignScenepoint() broken SP_PB3
BINKS: AlignScenepoint() broken BINKSROAM2
SHIVERS: AlignScenepoint() broken SHIVERSROAM
Search_Create cannot reach destination
MOTORHEAD: m_SearchStatus == CAI_Pathfinder::INVALID
```

`Using plain pathfinder` — норма (`GAME_VPUPATHFINDER` по умолчанию 0 вне
консолей, `WServer_World.cpp:1017-1021`), не след.

**ПОПРАВКА (уточнение пользователя, 2026-08-03):** это НЕ общая картина и
не объяснение скольжения. Наблюдение с экрана: ходячие **скользят, но до
целей доходят**; персонаж в кулачном бою нормально находит игрока и
приближается к нему. То есть навигация в основном работает, а перечисленные
строки — единичные отказы, а не системный сбой. Понижено до фонового
дефекта: «скольжение» = нет анимации ходьбы при рабочем перемещении, и это
куст анимации, а не навигации.

`AlignScenepoint() broken` (`AI_Action.cpp:9632`) остаётся любопытным:
санити-чек после успешного разворота к сценпоинту показывает `GetLookDir()`
вне дуги. Это отдельная мелкая задача.

Зонд `[NAV]` (см. §10) всё равно оставлен — две строки на загрузку мира,
цена нулевая, а «навграф пустой» до сих пор ни разу не мерили.

### 9.5 Мелочь, чтобы не гоняться второй раз

`(CWObject_Character::Char_ProcessControl) Unknown control: 25` (×4) —
это `CONTROL_UPDATE_CD_AUTOAIMVAL`: при выключенном
`WADDITIONALCAMERACONTROL` (закомментирован в `WClass.h:102`) нумерация
даёт 25, а `switch` в `WObj_Char.cpp:4115` его не обрабатывает. Так и в
исходнике — рассинхрона enum'ов между модулями нет. Безвредно.

## 11. Звук как корень: план починки (2026-08-03)

Решение по приоритету: чинить сначала звук, потому что скрипты и диалоги
завязаны на него напрямую (§9.3), а звуковая подсистема заведомо доделана
частично (`CLAUDE.md`, Фаза 7: M0-M2).

### 11.1 Что известно точно

* вывод звука работает — микшер, SDL-устройство, Vorbis-кодек, голоса
  (Фаза 7 M2), часть реплик слышна;
* сломана **база дескрипторов**: 177 уникальных имён дают
  `WARNING: Undefined sound: SND:<имя>` в одном прогоне;
* цепочка отказа: нет дескриптора → `CWRes_Sound::GetSound()` = NULL →
  `GetSampleLengthBuf` = 0 → `<NPC> failed Dialogue` → реплика не идёт;
* PC-контейнеры волн **не содержат** бинарной секции SFXDESC; дескрипторы
  лежат текстом в `Content/SfxDesc/*.xsfxc` и разбираются **нашим**
  парсером `NSFXDescScript` (`MSound_SFXDesc.cpp`) — это порт-хак, ретейл
  читал их через `CWaveContext::ReadSfxDesc`;
* прочитаны все 275 файлов, собрано 23033 дескриптора — значит парсер
  работает, но покрывает не всё.

Сборка не консольная, поэтому `USE_HASHED_SFXDESC`/`USE_HASHED_WAVENAME`
НЕ определены (`MSound.h:32-37`): имена волн и дескрипторов — настоящие
строки, сравнение регистронезависимое. Версия «всё хэшируется» закрыта.

### 11.2 Развилка, которую надо снять первой

По `Undefined sound` невозможно отличить два принципиально разных случая:

| | Значит | Чинится |
|---|---|---|
| **волна есть в контейнере** | дескриптор не собрался | наш парсер `.xsfxc` |
| **волны нет нигде** | дыра в наборе либо другая конвенция имён | ничем/иначе |

Зонд `[SFX] miss '<имя>' wave=YES in <контейнер> / wave=NO` отвечает на это
одной строкой на имя (`WDataRes_Sound.cpp`, `CWRes_Sound::OnLoad`).

### 11.3 Подозреваемые в парсере, по убыванию

1. **Синтаксис `*Source`, который `WildcardMatch` не понимает.** Мы
   поддерживаем только `*` и `;`-разделение. Счётчик
   `desc nodes: N total, X without *Source, Y with *Source but no matching wave`
   плюс печать ключей у пропущенных узлов (`[SFX] desc skipped`) показывает
   это прямо.
2. **Узлы, которых мы не знаем вовсе.** Под `*SFXDESCS` мы обрабатываем
   только `*DESC` и `*MATERIALDESC`, остальное молча пропускалось —
   теперь считается и называется (`[SFX] unknown node '*<ключ>'`).
3. **Конвенция имён волн в контейнере.** `[SFX] wc '<файл>' waves=N
   first='…','…','…'` по восьми диалоговым контейнерам (`D_*.xwc`)
   показывает, как волны названы на самом деле.
4. **Группировка вариантов.** `StripVariantSuffix` снимает только `_NN`.
   В списке промахов есть `Gam_drk_crp01` (цифры без подчёркивания),
   `hall_lrg_` и `dor_` (имя с висящим `_`), `d_fig_ghostdrone_brth_quick|2`
   (суффикс `|N`) — три разные конвенции, ни одна не покрыта.
   Это правится, только когда известно, как имена лежат в контейнере (п. 3).

### 11.4 Порядок работ

1. прогон с зондами ниже → снять развилку §11.2 и увидеть, какой из
   четырёх подозреваемых реален;
2. починить парсер под найденный синтаксис (правка локальная, один файл);
3. перепроверить по числу `Undefined sound` в следующем прогоне — это
   прямая метрика;
4. только после этого возвращаться к анимграфу: часть «замираний» может
   оказаться ожиданием реплики, которая никогда не начинается.

Быстрая альтернатива прогону: прислать в репозиторий два-три файла
`Content/SfxDesc/*.xsfxc` (например `D_Riddick.xsfxc` и любой из `Env_*`) —
по ним синтаксис виден сразу, без цикла сборки.

## 14. Влияет ли TimeScale на скорость передвижения — ДА, линейно

Вопрос от пользователя (2026-08-03): «все персонажи очень быстро скользят
по полу, быстрее чем должны; бегущий вообще перемещается из точки в точку
за доли секунды — может ли ускорение анимации на это влиять?»

**Может, и это не побочный эффект, а сам механизм.**

### 14.1 Откуда берётся перемещение

Персонажи в этом движке двигаются **корневым движением анимации**
(root motion), а не физической скоростью. `CWAG2I::GetAnimVelocity`
(`WAG2I.cpp:975-995`):

```cpp
CMTime TimeA = CMTime::CreateFromSeconds(Layer.m_Time);
fp32 TimeSpan = _pContext->m_TimeSpan;              // = GetGameTickTime() = 1/30 c
Layer.m_spSequence->EvalTrack0(TimeA, MoveA, RotA);
CMTime TimeB = GetLoopedTime(TimeA + CMTime::CreateFromSeconds(TimeSpan * Layer.m_TimeScale));
Layer.m_spSequence->EvalTrack0(TimeB, MoveB, RotB);
dMove = MoveB - MoveA;                              // смещение ЗА ТИК
```

`TimeScale` умножает **ширину окна выборки**, значит и пройденный путь:

```
units/сек = скорость_клипа * TimeScale
```

(смещение применяется как перемещение за тик без dt — измерено 2026-07-30,
`real/anim = 1.000`, `Docs/Research_MoveSpeed_Report.md`).

Так что `scale=4.000`, замеченный в `[ANIMT]` у анимаций 310/312/313,
означает буквально «этот персонаж движется вчетверо быстрее, чем идёт
клип».

### 14.2 Почему это САМО ПО СЕБЕ ещё не баг

Тарировка задумана самосокращающейся. `EnterState_InitSyncVelocity`
(`WAG2I_StateInst.cpp:500-521`) ставит

```
m_TimeScale = DestSpeed / AnimSpeed
```

где `AnimSpeed` — натуральная скорость клипа по корневому треку. Тогда

```
скорость = AnimSpeed * TimeScale = DestSpeed
```

то есть ровно то, что запросил AI, независимо от клипа. Если же
`TimeScale` авторский (`pAnimLayer->GetTimeScale()`), сокращения нет и
четвёрка — намеренная («играть вчетверо быстрее и двигаться вчетверо
быстрее»).

Поэтому вопрос не «влияет ли», а **замыкается ли петля**. Три величины
это решают, и все три теперь печатаются:

```
[ANIMV] obj= layer= t= scale= span= dMove= got= want= ratio= blend= loop=
```

`want` = `GetDestinationSpeed()` (сколько хотел AI, units/сек),
`got` = `|dMove| / TimeSpan` (сколько просит анимация),
`ratio` = `got/want`. Единица — петля замыкается, дефект не здесь;
`ratio` в 3-6 — нашли, и величина сразу назовёт множитель.

### 14.3 Второй вход в тот же вопрос

Зонд `[SEQ]` дополнен корневым треком:

```
[SEQ] ... rootLen=<путь за весь клип> clipSpeed=<rootLen/dur>
```

`clipSpeed` — натуральная скорость клипа в units/сек прямо из данных.
Её можно сверить с настройками персонажа (`m_Speed_Forward`,
`WObj_CharClientData.cpp:354`). Если `clipSpeed` завышена — врёт **декодер
move-трека** в `.XSA`, и тогда «слишком быстро» и «поза не меняется» —
один дефект в одном загрузчике, а не два разных.

### 14.4 Чего это НЕ объясняет

Завышенный `TimeScale` заставил бы анимацию проигрываться **быстро**, а не
замирать. Наблюдается же «поза первого кадра» плюс избыточная скорость.
Значит либо дефекта два, либо один дефект бьёт по корневому треку и по
костным трекам по-разному — и вот последнее ровно то, что различает
`[SEQ]`: `animatedRot` (костные повороты) против `rootLen` (корневой трек).

```
[SEQ] dur=1.833 nRot=3   nMove=3  animatedRot=1  identityAt0=3  firstAnim=2 layers=1
```

**50 из 70 треков поворота реально меняются между `t=0` и `t=dur/2`.**
Загрузчик `.XSA` читает данные правильно, клипы не плоские. Последняя

Побочно подтвердилось старое наблюдение `bones=120 / nodes=70`: один и тот
же клип (`dur=2.734`) даёт `animatedRot=50` и на 70-слотовом скелете, и на
120-слотовом, а `identityAt0` растёт с 16 до 66. То есть у 120-слотового
рига 70 слотов поворота клип не покрывает вовсе — они держат то, что
осталось от предыдущего кадра. Это отдельный известный дефект
(`Docs/Research_BoneAnimation.md`, «хвост QNaN»), не причина скольжения.

### 15.1 Вся цепочка измерена и здорова

| Уровень | Состояние | Чем измерено |
|---|---|---|
| AI/скрипты → анимграф | цел | `[AG2] req`, ноль отказов |
| граф состояний | цел | штатная трасса, 557 входов |
| привязка анимации | цела | `iAnim` резолвится |
| время слоя | цело | `[ANIMT]`, растёт и зацикливается, srv+cli |
| выборка треков `.XSA` | **цела** | `[SEQ]`, animatedRot 50/70 |
| блендинг/палитра/скиннинг | цел | замеры 2026-07-30 |

Не осталось ни одного звена, где анимация могла бы «замереть». Значит
исходная формулировка симптома была неточной.

### 15.2 Переформулировка: дефект, скорее всего, ОДИН — скорость

Наблюдения пользователя, собранные вместе:

* все персонажи скользят по полу **быстрее, чем должны**;
* бегущий перемещается из точки в точку **за доли секунды**;
* поза при этом выглядит как «первый кадр ходьбы».

Если перемещение завышено в несколько раз, а ходовой цикл идёт со
штатной скоростью, картинка и будет ровно такой: ноги переступают, но
персонаж уезжает из-под них — это и есть скольжение. А при беге с
кратным превышением персонаж пересекает комнату быстрее, чем цикл успевает
проиграться, и поза читается как застывшая.

То есть «анимация не играет» — это, вероятно, **следствие завышенной
скорости**, а не отдельный дефект. Такая трактовка единственная, что
согласуется со всеми шестью замерами выше.

Проверяется парой чисел из §14:

* `[ANIMV] … got= want= ratio=` — `ratio = 1` означает, что петля
  `DestSpeed/AnimSpeed` замыкается и скорость честная; `ratio` в 3-6 даёт
  множитель прямо в руки;
* `[SEQ] … rootLen= clipSpeed=` — натуральная скорость клипа из данных.
  Если завышена она, врёт декодер move-трека, и тогда «слишком быстро»
  объясняется тем же загрузчиком, чьи rotation-треки в порядке.

## 16. НАЙДЕНО: NaN в тарировке синхронных анимаций (2026-08-03, прогон #5)

`RIDDICK_DBG_ANIMV=1` дал ответ первой же строкой:

```
[ANIMV] obj=78  layer=0 t=0.000 scale=-nan  span=0.0333 dMove=44.642  got=1339.3 loop=1
[ANIMV] obj=85  layer=0 t=0.000 scale=-nan  span=0.0333 dMove=45.939  got=1378.2 loop=1
[ANIMV] obj=174 layer=0 t=0.000 scale=-nan  span=0.0333 dMove=116.965 got=3509.0 loop=1
[ANIMV] obj=85  layer=1 t=0.000 scale=4.000 span=0.0333 dMove=4.168   got=125.0  loop=0   <- здоровая
```

**`scale=-nan`.** Здоровая скорость — 125 units/с, у NaN-слоёв 1339 и 3509,
то есть в 10-28 раз больше.

Для сверки, `[SEQ]` подтвердил, что данные клипов нормальные:

```
[SEQ] dur=0.884 nRot=120 animatedRot=24 rootLen=115.44 clipSpeed=130.7
```

130.7 units/с — ровно то, что положено бегущему персонажу
(`m_Speed_Forward` = 12 → ≈120 units/с). Декодер `.XSA` не врёт ни в
поворотах, ни в корневом треке.

### 16.1 Где рождается NaN

`CWAG2I_StateInstance::UpdateSyncAnimScale` (`WAG2I_StateInst.cpp:~627`).
Состояния с двумя анимациями (ходьба/бег — их синхронизируют между собой)
режут клип по syncpoint'ам и на каждый отрезок считают свой масштаб
времени:

```cpp
fp32 TimeDiv = 1.0f / (Time - PrevTime);          // деление НЕ защищено
m_lTimeScales1[i] = (m_SyncPoints1.m_lPoints[i].m_Time - PrevTime1) * TimeDiv;
```

Если два соседних syncpoint'а совпали по времени, знаменатель ноль:
числитель тоже ноль → `0 * inf` = **NaN**; числитель не ноль → `inf`.

Рядом нашлось второе незащищённое деление того же рода —
`EnterState_InitSyncVelocity:520`: `m_TimeScale = DestSpeed / AnimSpeed`
при `AnimSpeed == 0` (клип без корневого движения).

### 16.2 Почему из этого следуют ОБА симптома

NaN расходится по двум веткам сразу, и каждая даёт своё наблюдение.

**Ветка позы.** `GetSyncAnimTime` умножает на этот масштаб и возвращает
NaN-время → `LoopedTime` = NaN → клип считается в NaN и отдаёт первый
кадр. **Поза замирает.** Проверки `if (LoopedTime < 0) LoopedTime = 0` это
не ловят: любое сравнение с NaN ложно.

**Ветка скорости.** `GetAnimVelocity` строит окно
`TimeB = TimeA + TimeSpan·NaN` = NaN. Дальше:

```cpp
bool bLooping = TimeB.Compare(TimeA) < 0;         // на NaN даёт «да»
if (bLooping) { GetTotalTrack0(LoopMove); dMove += LoopMove; }
```

то есть к смещению **за один тик** прибавляется путь за **весь клип**.
Отсюда 3509 units/с вместо 125. **Персонаж улетает.**

Вместе это ровно то, что видно на экране: ноги стоят в первом кадре, а
персонаж уезжает из-под них; на беге — «перемещение из точки в точку за
доли секунды».

### 16.3 Что сделано

1. `Riddick_SyncSliceOK` — вырожденный отрезок (`Time - PrevTime <= 1e-6`)
   больше не делит на ноль, масштаб такого отрезка = 1.0 (натуральный
   темп вместо NaN). Один раз печатает сами syncpoint'ы:
   `[SYNC] degenerate slice i= /  iState= Time= PrevTime= dur1= dur2=`
   плюс списки времён обеих последовательностей.
2. Гард на `AnimSpeed <= 1e-6` в `EnterState_InitSyncVelocity`.
3. Санитайз нефинитного масштаба в `GetAnimVelocity` и нефинитного времени
   слоя в `GetAnimLayers` (все 4 точки) с разовым `[ANIMNAN]`.

### 16.4 Что это ещё НЕ закрывает

Гард убирает NaN, но не отвечает, **почему syncpoint'ы вырождены**. Две
версии, и `[SYNC]` их различает по напечатанным временам:

* времена нулевые или все одинаковые → syncpoint'ы читаются неверно из
  `.XSA` (ключи `ANIM_EVENT_TYPE_SYNC`, `XRAnim.cpp:1587`,
  `pKey->m_AbsTime`) — тогда чинить надо загрузчик, а синхронизация двух
  клипов всё равно будет работать неправильно;
* времена осмысленные и лишь пара точек совпала → данные такие и есть,
  гард достаточен.

Поэтому следующий прогон нужен с тем же `RIDDICK_DBG_ANIMV=1` (проверить,
что `scale=-nan` исчез и `ratio` стал осмысленным) плюс новыми `[SYNC]` и
`[ANIMNAN]`.

## 17. Источник NaN найден в ИГРОВОМ коде (2026-08-03, прогон #6)

Гарды из §16 сработали не туда, куда я ожидал, и это оказалось полезно.

```
[SYNC]    0 строк          <- Riddick_SyncSliceOK НЕ срабатывал ни разу
[ANIMNAN] 8 строк (кап)    <- нефинитный масштаб слоя всё равно приходит
[ANIMV]   scale=1.000 x95, scale=4.000 x25, got максимум 195 units/с
```

Три вывода сразу:

1. **§16 был не тем местом.** Незащищённое деление в `UpdateSyncAnimScale`
   реально существует, но в этом контенте не срабатывает — NaN приходит
   откуда-то ещё.
2. **Катастрофическая скорость вылечена.** Было `got=3509 units/с`, стало
   максимум 195 — санитайз в `GetAnimVelocity` убрал ложное срабатывание
   компенсации шва петли. Это подтверждает механизм из §16.2, даже если
   источник NaN был другой.
3. **Замирание осталось — и теперь это делает мой же гард.** Нефинитное
   время слоя я клампил в ноль, то есть NaN превращался в честный первый
   кадр. Пока источник не убран, поза так и будет стоять.

### 17.1 Настоящее деление

`WObj_CharClientData.cpp:1237`, игровой код:

```cpp
m_AnimGraph2.SetAdaptiveTimeScale(
    MoveVel * 20.0f / m_AnimGraph2.GetPropertyFloat(PROPERTY_FLOAT_ANIMMOVELENGTH));
```

Знаменатель — длина корневого движения клипа за весь проигрыш. Пишется она
один раз, в `CWAG2I_StateInstance::EnterState_AdaptiveTimeScale`:

```cpp
pAnimLayerSeq1->EvalTrack0(CMTime::CreateFromSeconds(m_Duration1), Move, Rot);
m_pAG2I->GetEvaluator()->SetPropertyFloat(pLayer->GetMergeOperator(), CVec4Dfp32(Move).Length());
```

Деление не защищено. При нулевом знаменателе:

* `MoveVel > 0` → **+inf** → `Min(4.0f, inf)` = **4.0**. Вот откуда
  `scale=4.000` в 25 строках из 120: масштаб упёрся в потолок, персонаж и
  анимация идут вчетверо быстрее положенного;
* `MoveVel == 0` → **0/0 = NaN** → замирание позы.

`Max/Min` NaN не отсеивают — любое сравнение с NaN ложно, поэтому он
проходил кламп насквозь.

И знаменатель действительно бывает нулевым: `[SEQ]` в этом же прогоне дал
**19 клипов из 24 с `rootLen=0.00`**.

### 17.2 Две причины нулевого знаменателя, и как их различить

* **у клипа честно нет корневого движения** — тогда тарировать нечего, и
  правильный масштаб 1.0;
* **длина записалась не в то свойство**. Индекс берётся из авторского поля
  `pLayer->GetMergeOperator()`, а игровой код делит на свойство **8**
  (`PROPERTY_FLOAT_ANIMMOVELENGTH`). Формат AG2 v6 мы читаем реверсом, и
  если `m_iMergeOperator` парсится неверно, свойство 8 остаётся нулевым
  для ВСЕХ adaptive-состояний. Это объяснило бы «все персонажи двигаются
  слишком быстро» одним махом.

Зонд `[ADAPT] enter iState= iAnim= prop= animMoveLen= dur=` печатает
именно `prop`. **`prop != 8` — значит виноват загрузчик AG2**, и это надо
чинить, а не глушить гардом.

### 17.3 Что сделано

* гард на нулевой знаменатель в `WObj_CharClientData.cpp` — масштаб 1.0
  вместо inf/NaN, плюс `[ADAPT] ANIMMOVELENGTH=… -> scale forced to 1.0`;
* явный отсев NaN в `UpdateAdaptiveTimeScale` перед `Max/Min`;
* `[ADAPT] enter …` в месте записи длины — тот самый `prop`.

### 17.4 Про версию «виноваты таймеры»

Проверено и не подтверждается:

* `[ANIMV]` печатает `span=0.0333` ровно, то есть длина тика правильная;
* `[ANIMT]` (§13) показал монотонное время слоя с корректным зацикливанием
  и на сервере, и на клиенте;
* `[RATE]` в июле дал `ratio` 0.98-1.05 на 17 замерах — часы симуляции
  идут в реальном времени (`Docs/HacksAndHooks.md`).

Главное же: **NaN не может родиться из точности таймера.** Он требует
`0/0`, `inf−inf` или неинициализированной памяти. Интуиция «предыдущий кадр
с тем же временем, что и следующий» верна по сути — это действительно
нулевой знаменатель, — но он не в часах, а в длине корневого движения
анимации.

## 18. Корень скорости: длина клипа пишется не в то свойство (прогон #7)

`[ADAPT]` ответил на оба вопроса сразу:

```
[ADAPT] ANIMMOVELENGTH=0.000000 (moveVel=0.000) -> scale forced to 1.0   x12
[ADAPT] enter iState=697 iAnim=74  prop=0 animMoveLen=44.642  dur=1.467
[ADAPT] enter iState=45  iAnim=2   prop=0 animMoveLen=64.047  dur=0.934
[ADAPT] enter iState=49  iAnim=6   prop=0 animMoveLen=115.443 dur=0.884
[ADAPT] enter iState=703 iAnim=81  prop=0 animMoveLen=116.965 dur=0.617
[ANIMNAN] 0 строк
```

* **длина корневого движения считается ВЕРНО** — 44.6 / 64.0 / 115.4 / 117.0
  для разных locomotion-клипов;
* **пишется она в свойство 0**, а игровой код делит на свойство **8**
  (`PROPERTY_FLOAT_ANIMMOVELENGTH`, `WObj_CharClientData.cpp:1237`);
* больше **никто во всём дереве** в свойство 8 не пишет — проверено грепом;
* значит знаменатель был нулевым **всегда**: `MoveVel>0` → `+inf` →
  `Min(4.0f, inf)` = 4.0 (все двигались вчетверо быстрее),
  `MoveVel==0` → `0/0` = NaN (замирание);
* `[ANIMNAN]` ноль — гарды прошлого коммита закрыли утечку NaN, скорость
  пользователь подтвердил как «похожую на правильную».

### 18.1 Загрузчик слоя НЕ виноват — сверено с ретейлом

`Docs/Decomp_Map.md`: `FUN_10390570` в `GameWorld_Win32_x86_dll_decomp.c` —
это `CXRAG2_AnimLayer::Read`, опознан по `Error_static("CXRAG2_StateAnim::
Read", "Unsupported version %.4x")` в `default:`. Его case 5/6 читает поля
в том же порядке и тех же размеров, что и мы: fp32, fp32, uint32, int16,
u8, u8, u8, u8 = 18 байт — ровно измеренный stride.

Единственное расхождение — **дефолт**: ретейловский `Clear()`
(`FUN_103904d0`) кладёт в `+0x10` значение `0xFF`, а у нас там
`AG2_ANIMLAYER_MERGEOPERATOR_BLEND` = `0x01`. На читаемые из файла поля не
влияет, но подтверждает семантику: `m_iMergeOperator` в этом движке —
**номер свойства** (`0xFF` = `AG2_PROPERTY_NULL`), а не enum операторов
смешивания. Именно так он и используется в двух местах `WAG2I_StateInst.cpp`.

Вывод: ноль в `prop` — это то, что реально лежит в PC-файле. А раз
шипнутый PC-билд как-то работал, значит он писал длину в свойство 8 иным
путём, чем этот PS3-снапшот исходников. Ещё одно расхождение
«исходники ↔ релиз», в один ряд с `.XW`, `XTC2`, `CImage v0x0400`, AG2 v6.

### 18.2 Что сделано

Ноль трактуется как «не задано» и длина пишется туда, откуда игра читает —
в свойство 8. Переопределяется `RIDDICK_ADAPTPROP=<n>`, `=-1` возвращает
прежнее поведение для A/B. Зонд теперь печатает и сырое значение:
`prop=8(raw 0)`.

Ожидаемый эффект: `scale` перестаёт упираться в 4.0 и становится
осмысленным отношением «скорость персонажа / скорость клипа», то есть
ходовой цикл синхронизируется с перемещением.

### 18.3 Что это НЕ чинит

Пользователь после прогона #7: скорость выправилась, но **анимации всё ещё
застывшие и атака не работает**. Значит остаётся отдельная причина, и
`prop`-фикс её не закрывает. Следующие кандидаты, по убыванию:

1. `scale` после фикса — если он стал 0 или околонулевым, время слоя почти
   не идёт, и поза выглядит замершей. Смотреть `[ANIMV] scale=` и
   `[ADAPT] enter`;
2. `PROPERTY_FLOAT_STATETIME` = 0 — мы затирали ЕГО длиной клипа всё это
   время (`prop=0`!). Это отдельная порча: состояния, которые смотрят на
   время состояния, получали вместо него 44…117. Условия переходов и
   таймауты атаки завязаны как раз на такие свойства — вот вероятная
   причина «не может атаковать»;
3. звук — отдельная ветка, к анимации отношения не имеет.

Пункт 2 сильный: `prop=0` не просто «не туда записали», а **записали
поверх свойства STATETIME**, которое движок использует для условий.

## 19. Переадресация в свойство 8 ОТМЕНЕНА экспериментом (прогон #8)

```
[ADAPT] enter iState=697 iAnim=74 prop=8(raw 0) animMoveLen=44.642 dur=1.467
[ANIMV] scale=1.000 x97, scale=0.001 x7, scale=0.000 x5, scale=0.002 x2
```

Наблюдение пользователя: **персонажи встали на месте**, только доворачиваются
вокруг оси.

Причина прозрачная и её надо было предвидеть. Adaptive-масштаб считается как
`MoveVel * 20 / ANIMMOVELENGTH`, где `MoveVel` — **фактическая** скорость
персонажа. А у NPC она берётся из корневого движения анимации, которое само
масштабируется этим же значением. Замкнув запись на то свойство, из которого
идёт чтение, я замкнул петлю на себя: стоит → MoveVel=0 → scale=0 → корневое
движение 0 → стоит. `scale=0.000/0.001` в логе — это она.

Откачено: по умолчанию пишем по авторскому индексу, как раньше.
`RIDDICK_ADAPTPROP=<n>` оставлен для экспериментов, но выключен.
Работающим остаётся гард на нулевой знаменатель (масштаб 1.0), который
пользователь подтвердил в прогоне #7 как дающий правильную скорость.

### 19.1 Проверка по декомпилу: флаги состояний читаются ВЕРНО

Раз prop=0 — это то, что в файле, напрашивалась версия: мы неверно читаем
флаги состояния, уходим в `EnterState_AdaptiveTimeScale` там, где ретейл
идёт по обычной ветке (`m_TimeScale = 1.0f`).

Сверено: `FUN_10390940` в `GameWorld_Win32_x86_dll_decomp.c` — это
`CXRAG2_State::Read` (опознан по `Error_static("CXRAG2_State::Read",
"Unsupported version %.4x")`). Раскладка — 2×uint32 флагов, 5×int16
индексов, 3×uint8, всего 21 байт — **совпадает с нашей полностью**
(`Docs/Decomp_Map.md`).

**Версия закрыта: флаги состояний мы читаем правильно**, adaptive-ветка
включается там же, где в ретейле.

### 19.2 Где мы сейчас

| Симптом | Состояние |
|---|---|
| скорость передвижения | **исправлена** (гард на нулевой знаменатель) |
| NaN в масштабе времени | **устранён** (`[ANIMNAN]` = 0) |
| анимация замирает | **остаётся**, и это исходный дефект, а не регрессия |
| NPC не атакует | остаётся |

Версия «prop=0 затирает `PROPERTY_FLOAT_STATETIME` и потому ломает
переходы» из §18.3 **пока не проверена** — при отключённой переадресации
запись по-прежнему идёт в свойство 0. Это следующий кандидат, и проверять
его надо не переадресацией записи (мы видели, чем это кончается), а
измерением: смотреть, что лежит в свойстве 0 и кто его читает.

### 19.3 Следующий шаг — измерять позу, а не время

Все замеры до сих пор касались входов: состояние, iAnim, время слоя,
данные клипа, скорость. Все они здоровы. Ни разу не измерялся **выход** —
меняется ли итоговая палитра костей между кадрами.

Для этого зонд уже есть и писать ничего не надо: `RIDDICK_DBG_BONES=1`
(`WTriMesh.cpp`, за `GetBoneTransforms()`) печатает
`[BONES] skel= bones= moving= static= staticIdx=[…]` раз в 60 вызовов.

Читать: `moving` близко к `bones` → скелет анимируется, и «замирание» —
вопрос к рендеру/скиннингу; `moving` = 0 или единицы → поза действительно
не меняется, и тогда сужать надо между `GetAnimLayers` (входы здоровы) и
палитрой.

## 20. НАЙДЕНО: у `SELECTION_CHAR` не было ветки активации (прогон #13)

Уровень `pa1_prisonarea`, `RIDDICK_DBG_SEL=1 RIDDICK_DBG_USE=1`.

```
[SEL]  iSel=74  type=1(base=1 invalid=0 proxy=0) close=74  name='BARBER'
[SEL]  iSel=85  type=1(base=1 invalid=0 proxy=0) close=85  name='MICHAELS'
[SEL]  iSel=104 type=1(base=1 invalid=0 proxy=0) close=104 name='JIMBO'
[USE]  find   iSel=74 iClose=-1 selType=0x1 name='BARBER'
[USE]  select iBest=74 name='BARBER' focusType=0x1 darkMask=0 tick=905 tgtCD=yes
```

Вся цепочка до нажатия **исправна**:

* отбор целей работает, NPC опознаётся как `SELECTION_CHAR` (=1);
* `focusType=0x1` — значит `OBJMSG_CHAR_GETUSENAME` вернул имя действия,
  то есть движок сам считает, что с этим NPC можно взаимодействовать
  (иначе `Char_ShowInFocusFrame` обнулил бы тип и объект);
* обработчик нажатия получает валидную цель и валидный `tgtCD`.

А дальше — `CWObject_Character::Char_ActivateStuff`
(`WObj_CharMechanics.cpp:5355`):

```cpp
switch (_SelType & SELECTION_MASK_TYPE)
{
case SELECTION_ACTIONCUTSCENELOCKED:
case SELECTION_ACTIONCUTSCENE: … OBJMSG_ACTIONCUTSCENE_ACTIVATE …
case SELECTION_PICKUP:         … OBJMSG_RPG_AVAILABLEPICKUP …
case SELECTION_LADDER:
case SELECTION_HANGRAIL:       … GrabLadder …
/*case SELECTION_DEADCHAR:     … закомментировано целиком … */
```

**Ветки `SELECTION_CHAR` здесь нет вообще.** Нажатие «использовать» на
персонаже молча уходит в `default` и не делает ничего. Это и есть «нельзя
начать диалог ни с одним NPC» — буквально, в одном `switch`.

### Как должно быть — видно этажом выше

В `Char_ShowInFocusFrame` (тот же файл, `:5272`) `case SELECTION_CHAR`
**намеренно проваливается** в блок `SELECTION_PICKUP` /
`SELECTION_ACTIONCUTSCENELOCKED`, который шлёт персонажу
`OBJMSG_ACTIONCUTSCENE_CANACTIVATE`. То есть в этом движке персонаж и есть
цель action-cutscene, его спрашивают тем же сообщением — значит и
активировать его надо тем же `OBJMSG_ACTIONCUTSCENE_ACTIVATE`.

Ровно это и добавлено: `case SELECTION_CHAR:` / `SELECTION_DEADCHAR:`
проваливается в ACS-ветку. `RIDDICK_CHAR_ACTIVATE=0` возвращает прежнее
поведение для A/B. **По умолчанию включено** — регрессии быть не может,
сейчас на этом месте не происходит вообще ничего.

Зонд `[USE] activate CHAR iSel= selType=` (20 строк) подтверждает, что
ветка сработала.

### Что осталось перепроверить

`SELECTION_FLAG_INVALID` оказался не гейтом способностей, а простым
тестом угла: `if (BestDot <= 0.0f) _SelType |= SELECTION_FLAG_INVALID`
(`WObj_CharMechanics.cpp:5131`). Мелькание `type=1` → `type=33` в логе —
это игрок чуть отвёл прицел, а не отказ. Версия закрыта.

### ПОПРАВКА: ветка сработала, но персонаж это сообщение не обрабатывает

Прогон #14: `[USE] activate CHAR iSel=74 selType=0x1` печатается (20 строк,
кап), то есть добавленная ветка работает и `OBJMSG_ACTIONCUTSCENE_ACTIVATE`
уходит персонажу. Диалог не начался.

Причина: **`CWObject_Character` не обрабатывает ни
`OBJMSG_ACTIONCUTSCENE_ACTIVATE`, ни `_CANACTIVATE`** — он их только шлёт.
Единственное упоминание `ACTIVATE` в `WObj_CharMsg.cpp:3187`
закомментировано. Обработчики есть у `WObj_ActionCutscene.cpp`.

И поправка к моему прежнему выводу: **`focusType=0x1` не доказывал**, что
с NPC можно взаимодействовать. Обработчик `OBJMSG_CHAR_GETUSENAME`
(`WObj_CharMsg.cpp:2174`) возвращает 1 безусловно, отдавая `m_UseName`,
который может быть пустым. Я прочитал это сильнее, чем следовало.

Флаг `RIDDICK_CHAR_ACTIVATE` переведён в **выключен по умолчанию**: как
no-op он безвреден, но выдавать его за починку нельзя.

### Куда переносится вопрос

Разговор с NPC в этом движке инициируется **не нажатием на самом
персонаже**, а отдельным объектом action-cutscene рядом с ним — он и
обрабатывает `CANACTIVATE`/`ACTIVATE`. Такие объекты в мире есть, лог их
показывает: `[SEL] iSel=29 type=3` — это `SELECTION_ACTIONCUTSCENE`.

Значит вопрос: **почему у говорящих NPC такой объект не попадает в выбор.**
Варианты: объекта нет в мире (скрипт/спавн), он есть но `CanActivate`
отказывает, либо `Char_FindStuff` предпочитает ему сам персонаж.

Зонд для этого уже есть и писать ничего не надо — `RIDDICK_DBG_AG2FX=1`
включает в числе прочего
`[ACS] canact obj= arc= dotLook= dotPos= csFlags= disabled= dependItem=
dependMsg= retry= tick=` (`WObj_ActionCutscene.cpp`, `CanActivate`) — это
главный гейт: по его результату `Char_FindStuff` ставит
`SELECTION_ACTIONCUTSCENE` либо `..._LOCKED`. Подробности —
`Docs/HacksAndHooks.md`.

## 21. НАЙДЕНО: пустой айтем обнулял хэш и ломал сортировку (прогон #15)

`[ACS] canact` в прогоне сработал **только для obj=29** — того самого, что
`[SEL]` показывает как `type=3` (`SELECTION_ACTIONCUTSCENE`). Ни для
BARBER, ни для MICHAELS, ни для JIMBO ACS-объект не запрашивается вовсе.
То есть ветка «диалог начинается через ACS-объект рядом с NPC» тоже не
подтверждается: таких объектов у говорящих NPC просто нет.

Зато в логе есть прямая улика по другому пути — тому, что AI заводит сам:

```
JIMBO failed Dialogue: IDLE_CALL Dialogueindex 712
HALEY failed Dialogue: IDLE_CALL Dialogueindex 718
```

а `[DLGLEN]` в более раннем прогоне на это отвечал
`no dialogue item (hash miss)`.

### Дефект

`CWRes_Dialogue::CreateFromRegistry` (`WDataRes_Sound.cpp:894`):

* айтемы сортируются **по хэшу** (`lDialogueItems.Sort()`, компаратор
  `CTempDialogue::Compare` сравнивает `m_Hash`);
* `GetHashPosition` ищет по `m_lDialogueIndexes` **двоичным поиском**, то
  есть требует строго возрастающих хэшей;
* а при переносе данных пустой айтем получал **`m_Hash = 0`**:

```cpp
else
{
    m_lDialogueIndexes[j].m_StartPos = 0;
    m_lDialogueIndexes[j].m_Size = 0;
    m_lDialogueIndexes[j].m_Hash = 0;      // <-- рвёт монотонность
}
```

Один такой айтем в середине ломает предусловие поиска, и `GetHashPosition`
начинает промахиваться по **существующим** репликам, которые лежат за ним.
Отсюда и «hash miss» на индексах вроде 712 при живом ресурсе.

Это **тот же класс дефекта, что уже чинили в звуке**:
`CWaveContainer_Plain::GetSFXDescIndex` — тоже двоичный поиск по списку,
который никто не сортировал (пришлось добавить `SortSFXDescs`).

### Правка

Сохраняем настоящий хэш и у пустых айтемов: сортировка остаётся целой,
а нулевой размер разбирается ниже по течению. По умолчанию включено,
`RIDDICK_DLGHASH=0` возвращает прежнее поведение для A/B.

Отчёт `[DLGSORT] '<диалог>' items=N empty=N unsorted=N` (12 строк, печатается
только при ненулевых) показывает масштаб: `unsorted>0` означает, что поиск
промахивался; после правки должно стать `unsorted=0` при том же `empty`.

## 22. ИТОГ по диалогам: подсистема РАБОТАЕТ (прогон #16)

`[DLGSORT]` — **ноль строк**. Значит ни в одном диалоговом ресурсе нет
пустых айтемов, монотонность хэшей нигде не нарушалась, и правка §21
оказалась **no-op на этом контенте**. Версия закрыта (правку оставил: она
всё равно корректнее, просто на данном наборе ничего не меняет).

И главное, что стоило посчитать давно:

```
проиграно реплик за прогон : 194
failed Dialogue            : 3
[DLGLEN] hash miss         : 3
```

**Диалоговая подсистема работает на 98.5%.** Три промаха на 194 реплики —
это не «диалоги сломаны», а отдельные дырки в контенте или индексах.
Формулировка «звук идёт, но диалоги не работают» была неверной с самого
начала, и я на ней слишком долго строил версии.

### Что тогда означает жалоба «нельзя начать диалог ни с одним NPC»

Это **разговор по инициативе игрока**, и он в этом коде вообще не
реализован как действие «использовать»:

* `Char_ActivateStuff` не имеет ветки `SELECTION_CHAR` (§20);
* `CWObject_Character` не обрабатывает `OBJMSG_ACTIONCUTSCENE_ACTIVATE`
  (§20, поправка);
* ACS-объектов рядом с говорящими NPC в мире нет — `[ACS] canact`
  срабатывает только на obj=29 (§21);
* при этом NPC исправно попадают в фокус как `SELECTION_CHAR`
  (16 раз за прогон).

То есть механизм, которым игрок начинает разговор, **нам пока неизвестен**,
и гадать по движку дальше бессмысленно — четыре версии подряд отвергнуты
замером (QNaN-топология, маски треков, ACS-объекты, сортировка хэшей).

### Как узнать, а не угадывать

1. **Ретейл.** Найти в `GameClasses_Win32_x86_dll_decomp.c` аналог
   `Char_ActivateStuff` (якорь: рядом должны быть вызовы с
   `OBJMSG_RPG_AVAILABLEPICKUP` и `GrabLadder`-подобной функцией) и
   посмотреть, есть ли там ветка для типа 1. Если есть — станет видно,
   какое сообщение шлётся.
2. **Контент.** В `Content/Dialogues/` у говорящих NPC есть `.xrg`; надо
   посмотреть, каким событием они запускаются — в самих файлах и в
   скриптах уровня (`.XW`).
3. **Наблюдение.** Проверить в оригинальной игре, как выглядит начало
   разговора: подсказка на экране, кнопка, автозапуск по подходу. Это
   сразу отсечёт половину вариантов.

Пока это не выяснено, править движок наугад не стоит.

## 23. РЕШЕНО: правильный адресат — `OBJMSG_CHAR_USE` → `OnUse` (2026-08-03)

Решающее уточнение от пользователя: при подходе к NPC **движок сам
показывает предложение** — «Поговорить с: Джимбо» слева внизу и имя
персонажа справа внизу.

Это меняет трактовку §20/§22. Раз подсказка рисуется, значит:

* `UseText` и `DescText` заполнены,
* `Char_ShowInFocusFrame` отработал и не обнулил тип,
* игра **сама заявляет игроку, что действие доступно**.

А обработчика нажатия у `SELECTION_CHAR` в `Char_ActivateStuff` нет — то
есть игра предлагает действие, которого не выполняет. Дыра подтверждена
окончательно.

### Правильный адресат найден

`CWObject_Character::OnUse(int _iUser, int _Param)`
(`WObj_CharMechanics.cpp:4157`) — это и есть обработчик разговора:

```cpp
CDialogueLink ApproachItem = Char_GetDialogueApproachItem();
if (ApproachItem.IsValid())
{
    Char_ActivateDialogueItem(ApproachItem, _iUser);
    m_LastUsedTick = m_pWServer->GetGameTick();
}
```

`Char_GetDialogueApproachItem` отдаёт `m_DialogueItems.m_Approach` (или
`m_ApproachScared` при высоком приоритете AI), а `Char_ActivateDialogueItem`
запускает реплику. Сами approach-айтемы расставляет диалоговый скрипт через
`OBJMSG_CHAR_SETDIALOGUEITEM_APPROACH` (`WObj_CharDialogue.cpp:897`).

Дотянуться до `OnUse` можно сообщением **`OBJMSG_CHAR_USE`**:
`WObj_CharMsg.cpp:1385` — `case OBJMSG_CHAR_USE: return OnUse(_Msg.m_iSender,
_Msg.m_Param0);`

Прошлая попытка слать `OBJMSG_ACTIONCUTSCENE_ACTIVATE` была мимо: персонаж
это сообщение не обрабатывает вовсе (§20, поправка).

### Что сделано

`case SELECTION_CHAR/SELECTION_DEADCHAR` в `Char_ActivateStuff` шлёт цели
`OBJMSG_CHAR_USE` с отправителем-игроком. Зонд печатает и **результат**:

```
[USE] activate CHAR iSel=74 selType=0x1 -> OBJMSG_CHAR_USE res=N
```

Читать: `res=1` — `OnUse` отработал до конца, approach-айтем найден и
активирован, разговор должен пойти; `res=0` — `OnUse` вышел раньше
(в частности, при `_Param < 0` это ветка выбора реплики), и тогда следующий
вопрос — валиден ли `ApproachItem`, то есть расставил ли их диалоговый
скрипт.

`RIDDICK_CHAR_ACTIVATE=0` возвращает прежнее поведение.

## §24. Подсказка над персонажем: focus-frame здоров, рендерер не портирован

**Прогон 17** (`pa1_prisonarea`, `RIDDICK_DBG_FOCUS=1 RIDDICK_DBG_SEL=1
RIDDICK_DBG_USE=1 RIDDICK_DBG_VIEW=1 RIDDICK_DBG_LETTERBOX=1`).

### Замер

```
[SEL]   iSel=74 type=1(base=1 invalid=0 proxy=0) close=74 name='BARBER'
[FOCUS] iObj=74 type=1 path=3 aiPrio=0x40 canAct=0 useNameOk=1
        use='§LCHAR_NAME_AI_PA1_INMATE_BARBER'
        desc='§LCHAR_DESC_AI_PA1_INMATE_BARBER'
[FOCUS] iObj=104 type=1 path=3 aiPrio=0x40 ... use='§LCHAR_NAME_AI_PA1_INMATE_JIMBO'
[FOCUS] iObj=29  type=3 path=0 ... useNameOk=1 use='§Lacs_name_flushtoilet'
```

`path=3` — нормальный проход `Char_ShowInFocusFrame` до ACS-блока;
`aiPrio=0x40` (`PRIO_IDLE`) — выход по AI-приоритету не сработал;
`useNameOk=1`, текст непуст. **Версия «виноват AI-приоритет» закрыта, вся
серверная часть focus-frame здорова.**

### Что оказалось ошибкой в постановке задачи

Мы сравнивали персонажа с унитазом как «одно и то же, только у одного
работает». Это неверно — подсказки приходят из разных мест:

| Объект | Источник подсказки |
|---|---|
| ACS (унитаз) | `pCD->m_ChoiceString` на `OBJMSG_CHAR_GETCHOICES` (`WObj_ActionCutscene.cpp:1028`) |
| персонаж | список `m_liDialogueChoice` на том же сообщении (`WObj_CharMsg.cpp:4927`); пустой → `nChoices=0` → клиент не рисует ничего |

А `UseText`/`DescText`, которые мы измеряли, **не рисует никто**: рендерер
focus-frame в исходниках выключен авторами —
`WObj_CharRender.cpp:1004`, `#if 0` с комментарием
«JK-NOTE: Focus frame is broken, do not use without rewrite».

### Сверка с ретейлом

В ретейле рендерер есть. `GameClasses_Win32_x86_dll_decomp.c:96628-96665`:

```c
pcVar3 = *(char **)(param_2 + 0x20);            // UseText
if (*pcVar3 == -0x59 /* 0xA7 = '§' */ && pcVar3[1] == 'L') bVar25 = true;
uVar32 = bVar25 ? 2 : 0;
while (pcVar3[uVar32]) { if (pcVar3[uVar32] == -0x59) { pcVar3[uVar32]=0; break; } uVar32++; }
if (Localize_KeyExists(bVar25 ? pcVar3+2 : pcVar3)) {
    Localize_Str(pcVar3, buf, 0x400);
    pcVar3 = *(char **)(param_2 + 0x24);        // DescText, так же
    ...
}                                                // ключа нет -> не рисуем ничего
```

То есть ретейл: снимает префикс `§L`, обрезает строку на следующем `§`,
проверяет ключ через `Localize_KeyExists` и рисует только при наличии.
Соответствие полей: `param_2+0x20` = `m_FocusFrameUseText`,
`param_2+0x24` = `m_FocusFrameDescText` (порядок и типы совпадают с
`WObj_CharClientData.h`). Записано в `Docs/Decomp_Map.md`.

### Следствие

Задача расщепилась на две независимые:

1. **Подсказка-«выбор»** (`m_liDialogueChoice`) — почему список пуст.
   Заполняется только из `EvalDialogueLink` при цели `player`
   (`WObj_CharDialogue.cpp:1131`). Меряем `RIDDICK_DBG_CHOICES=1` +
   штатной трассой `RIDDICK_DBG_DLG=1`.
2. **Focus-frame HUD** — не портирован вовсе. Восстанавливать по
   декомпилу выше; работа отдельная и после того, как заработают диалоги.

### Побочный результат: кинополосы

`RIDDICK_DBG_LETTERBOX=1` не дал **ни одной** строки, хотя зонд стоял
внутри блока отрисовки полос и флаг был в баннере `[FLAGS]`. Единственное
место, где движок рисует кинополосы (`XREngine.cpp:4898`, под
`XR_VIEWFLAGS_WIDESCREEN`), не выполняется. Чёрная полоса внизу экрана —
не они.

### Где обрыв

После `[USE] res=1` трасса даёт `Clear listener` (это первая строка
`Char_ActivateDialogueItem`) — и **тишину**. Ни `PlayDialogue_Hash` у NPC,
ни `BeginDialogue`/`PlayDialogue_Hash` у игрока.

Так выглядит ранний выход из `PlayDialogue_Hash`: его штатная строка трассы
стоит **в конце** функции, а выходов до неё пять
(`WObj_CharDialogue.cpp:593-613`: нет ресурса, нет айтема по хэшу, персонаж
мёртв, занят токен, приоритет ниже AI). Каждый теперь печатает свою причину
(`PlayDialogue_Hash: %08X FAIL (...)`), плюс добавлены строки
`ActivateItem: hash= isPlayer= selfHash= selfValid= bBegin=` и
`BeginDialogue: speaker= startItem=`.

### Список выборов пуст — следствие, а не причина

`[CHOICES] char obj=74 nChoices=0 dlgTick=702`: `m_DialogueChoiceTick`
изменился с −1 на 702, то есть `EvalDialogueLink` в ветке цели `player`
(`WObj_CharDialogue.cpp:1131`) **выполнялся**, но не добавил ни одного
линка. Подсказки нет потому, что нет выборов, а выборов нет потому, что
реплика не запустилась.

### Побочное наблюдение: направляющий тест смотрит не туда

```
[23.40, Char 74, BARBER], Resetting listener because of failed tests
   (Distance: 66.4 [64.0], DirCheck1: -0.9 [0.1], DirCheck2: -0.7 [-0.2]
```

`DirCheck1 = -Dot2(MeToPlayer, PlayerLook)` (игрок смотрит на меня),
`DirCheck2 = Dot2(MeToPlayer, MyLook)` (игрок там, куда смотрю я)
— оба сильно **отрицательные** там, где ожидаются положительные. Один
перевёрнутый знак у `MeToPlayer` объясняет обе цифры разом, и это
соседствует с жалобой на повёрнутые прожекторы и дёргающиеся камеры.

Оговорка: тривиальное объяснение тоже подходит — игрок отошёл (66.4 при
пороге 64.0) и отвернулся. Различить можно только по сырым векторам,
поэтому в ту же строку добавлена печать `MeToPlayer/PlayerLook/MyLook/
MyPos/PlayerPos`. **Пока это не подтверждено — версия, а не вывод.**

## §26. Найдена причина: ведущий минус в имени диалогового айтема

**Прогон 19** (`pa1_prisonarea`, те же флаги). Расширенная трасса дала
цепочку целиком:

```
[26.20, Char 74, BARBER],  Clear listener. (old: 2559, $PLAYER)
[26.20, Char 74, BARBER],  ActivateItem: hash=7C767E5E isPlayer=0 selfHash=00000000 selfValid=0 bBegin=1 iUser=2559
[26.20, Char 2559, $PLAYER], BeginDialogue: speaker=74 startItem=7C767E5E
[26.20, Char 2559, $PLAYER], PlayDialogue_Hash: 7C767E5E FAIL (no such item in dialogue resource)
```

### Как опознан хэш

`StringToHash` = `CStrBase::StrHash` (`MRTC_String.h:690`) — djb2 с
приведением к нижнему регистру (`MRTC_StrBase.cpp:1614`):
`h = h*33 + tolower(c)`, старт `5381`, в конце `-= 5381`. Функция обратима
перебором: четырёхсимвольные строки лежат в диапазоне `0x7Cxx_xxxx`,
трёхсимвольные — в `0x0B87_xxxx`.

Перебор дал единственное осмысленное решение: `7C767E5E` = **`"-100"`**.

Проверка сходится и с другой стороны: `hash("100") = 0B8774B1`, а эта
строка в том же логе играется успешно у трёх разных NPC:

```
[6.03,  Char 86, ABE],    PlayDialogue_Hash: 0B8774B1 (result: 1)!
[9.00,  Char 88, VICTOR], PlayDialogue_Hash: 0B8774B1 (result: 1)!
```

Заодно расшифровались и остальные хэши из логов: `0B87759E`="176",
`0B878E40`="709", `0B878E5B`="713". Реплики нумерованные, у каждого
персонажа свой файл диалогов.

### Почему минус доезжал до хэша

Минус — разделитель, означающий «эту реплику говорит игрок». Два из трёх
путей движка снимают его сами:

| Путь | Обработка `'-'` |
|---|---|
| `0x1020 _APPROACH_OLD` (`WObj_CharMsg.cpp:1517`) | `Set(CFStrF("%i", Abs(Param0)), (Param0 > 0))` — знак в `Param0` |
| `EvalDialogueLink` (`WObj_CharDialogue.cpp:919-928`) | `pData = Str() + 1`, `Param0 = Flip ^ 1` |
| **`0x1021 SetApproachItem` через SimpleMessage** | **никак — строка уходит как есть** |

Третий путь — это скрипты карты: `CWO_SimpleMessage::Parse`
(`WObj_SimpleMessage.cpp:33`) режет строку по `;` и кладёт хвост в
`m_StrParam`, а `CreateMessage` отдаёт его в `m_pData` без изменений.
Именно им уровень раздаёт NPC approach-реплики — поэтому в трассе и не
было строк `SetItem` из `EvalDialogueLink`, а `approach=1` при этом был.

### Правка

`Riddick_SetDialogueItem` (`WObj_CharMsg.cpp`) снимает ведущий `'-'` и
ставит `bIsPlayer = false` — ровно как два других пути. Применено ко всем
шести айтемам. Флаг отката `RIDDICK_DLGITEM_MINUS=0`.

Ожидаемо после правки: `[SETITEM] ... stripped=1 hash=0B8774B1`, затем
`PlayDialogue_Hash: 0B8774B1 (result: 1)` у игрока, `EvalDialogueLink` с
целью `player` и непустой `m_liDialogueChoice` — то есть появившаяся
подсказка выбора реплик.

### Оставшийся отдельный дефект

`[26.23, Char 74, BARBER], PlayDialogue_Hash: 0B878E5B FAIL` — у BARBER
нет айтема «713» в собственном файле диалогов. Это тот же случай, что
`failed Dialogue: IDLE_CALL Dialogueindex 711` из прежних логов; к
разговору по инициативе игрока отношения не имеет.

## §27. Сверка с декомпилом: правка §26 была наполовину неверной

По требованию «сверяйся с декомпилом» вывод §26 проверен по
`GameClasses_Win32_x86_dll_decomp.c`. Минус действительно лишний, но
**место правки и полярность флага были другими**.

### Метод

`FUN_10003140` — это `CStrBase::StrHash` (побайтово совпадает с
`MRTC_StrBase.cpp:1614`: djb2 ×0x21, свёртка регистра, ±0x1505). Значит
любой хэш-литерал в декомпиле можно раскрыть обратным перебором. Ghidra
выбирает ветки разбора ключей именно по этим литералам — так опознаётся
каждая ветка без единой догадки.

### Что нашлось

`FUN_102b5350` = `CCharDialogueItems::Parse`. Шесть веток, все ключи
раскрыты перебором и сошлись со смещениями слотов
(`m_DialogueItems` = +0x324 в персонаже):

| Хэш | Ключ | Слот | Ретейл |
|---|---|---|---|
| `409274C7` | `approachdialogueitem` | +0 | **число** → `StrHash("%d")`, `bIsPlayer = (value < 0)` |
| `5B0CA3E6` | `dialogueitem_approach` | +0 | строка, флаг 1 |
| `CB507677` | `dialogueitem_approach_scared` | +8 | строка, флаг 1 |
| `7FD54113` | `dialogueitem_threaten` | +0x10 | строка, флаг 1 |
| `9673EA1C` | `dialogueitem_ignore` | +0x18 | строка, флаг 1 |
| `B8471D3F` | `dialogueitem_timeout` | +0x20 | строка, флаг 1 |
| `93C266B2` | `dialogueitem_exit` | +0x28 | строка, флаг 1 |

Смещения независимо подтверждает `Char_DebugDialogueInfo`
(декомпил, строка 473986): рядом с ними лежат литералы `"Approach"`,
`"Scared"`, `"Threaten"`, `"Ignore"`, `"Timeout"`.

### Вывод

Наш снапшот расходится с ретейлом **ровно в одной ветке** — легаси-ключе
`APPROACHDIALOGUEITEM` (`WObj_CharCreate.cpp:46`):

```cpp
m_Approach.Set(_KeyValue, false);   // строка целиком + флаг всегда false
```

Ретейл на том же ключе:

```c
iVar2 = GetValuei(...);              // читаем как ЧИСЛО
str   = CStrF("%d", ...);            // обратно в строку
*(bool*)(this + 4) = iVar2 < 0;      // флаг = ЗНАК
*(int*)this        = StrHash(str);
```

Для карты со значением `-100` это даёт имя `"100"` и `bIsPlayer = true`.
То есть у нас было **две** ошибки, а не одна:

1. имя `"-100"` вместо `"100"` (§26 — верно);
2. `bIsPlayer = false` вместо `true` — из-за чего реплику искали в файле
   диалогов **игрока**, тогда как говорить её должен сам NPC из своего
   файла. Это согласуется с логом: айтем «100» успешно играют ABE, VICTOR
   и VICTIM — каждый из своего файла.

Правка §26 исправляла только (1) и в message-пути, до которого дело,
по-видимому, вообще не доходит. Исправлено: числовой разбор в
`CCharDialogueItems::Parse` как в ретейле (только когда значение
действительно число), message-путь приведён к той же конвенции.

### Попутная находка

Ретейловый `Char_GetDialogueApproachItem` (`FUN_102e7e60`) имеет **третью**
ветку, которой нет в нашем исходнике: при флаге AI-состояния `0x400` он
отдаёт слот Threaten (+0x10) и возвращает вызывающему флаги `0x1800`.
У нас есть только проверка приоритета. Записано в `Docs/Decomp_Map.md`.

```cpp
if(b3PI) { CNetMsg Msg(PLAYER_NETMSG_SETDIALOGUECHOICES); ... }
```

`SetDialogueChoices: '<строка>' parsed= iPlayer= 3PIMode=` (последнее звено
перед экраном).

## §30. Найдена причина обрыва: имя игрока стиралось

**Прогон 22.** Замер закрыл сразу две версии и дал точную причину.

### Версия про перевёрнутые матрицы — НЕ подтвердилась

```
[3PI] iFocus=74 eFocus=3 mode=0 b3PI=0 enough=1 dist=1.0 focusAmt=0.61 dirCheck2=0.51 moving=0 choices=0 speaking=0
[3PI] iFocus=74 eFocus=3 mode=2 b3PI=1 enough=1 dist=1.0 focusAmt=0.76 dirCheck2=0.95 moving=0 choices=0 speaking=0
```

`dirCheck2` **положительный** (0.51…0.95) при пороге +0.2, `enough=1`, и
игрок **входит** в 3PI-режим диалога (`mode=2 b3PI=1`). Гейт фокуса цел;
подозрение на битые матрицы ориентации в этом месте снято.

(Побочно видно, что `dist` всегда ровно 1.0: `DistanceToObject` считается
как `Min(dist, CamToObjZ.Length())`, а `CamToObjZ` строится из уже
**нормированного** `CamToObj`. Это поведение самого движка, тест
расстояния из-за него всегда проходит. Не наш дефект, но знать полезно.)

### Причина

```
LinkTarget: 'Victor'  -> iTarget=88   items='100'
LinkTarget: 'Victim'  -> iTarget=87   items='100'
LinkTarget: 'Abe'     -> iTarget=86   items='101'
LinkTarget: 'Riddick' -> iTarget=0    items='99'
```

Линки диалогов адресуются **по имени объекта**. У NPC имена резолвятся, у
игрока — нет. Дальше `EvalDialogueLink` при `iTarget <= 0` уходит в ветку
«цель не найдена» и обрывает разговор (`SETDIALOGUETOKENHOLDER, -1`),
поэтому `Char_SetDialogueChoices` для игрока не вызывается вовсе:

```
SetDialogueChoices: '100' parsed=1 iPlayer=-1 3PIMode=0 sender=86 owner=0
SetDialogueChoices: '100' parsed=1 iPlayer=-1 3PIMode=0 sender=88 owner=0
SetDialogueChoices: '101' parsed=1 iPlayer=-1 3PIMode=0 sender=87 owner=0
```

— три вызова, все на NPC (`iPlayer=-1`), ни одного на игрока.

Причина, почему имя не находится: ключ `PLAYERNR`
(`WObj_CharCreate.cpp:1181`) делал

```cpp
m_pWServer->Object_SetName(m_iObject, "$PLAYER");
```

а `Object_SetName` **переименовывает** — снимает старый узел из
`m_NameSearchTree` и ставит новый (`WServer_Obj.cpp:262-287`). Имя, данное
карте персонажу игрока, пропадало.

### Почему это правка, а не подгонка

* `$PLAYER` не используется в исходниках больше **нигде** (единственное
  вхождение — эта строка);
* любая цель на `$` разбирается раньше поиска по имени:
  `ResolveSpecialTargetName` отдаёт для `$player` отдельный
  `SPECIAL_TARGET_PLAYER` (`WObj_SimpleMessage.cpp:423-441`), так что имя
  `$PLAYER` в дереве имён не нужно ни одному пути;
* в декомпиле ретейла строки `"$PLAYER"` **нет ни в одном из пяти
  модулей**, при том что строковые литералы Ghidra здесь выводит (`"$ROOM"`,
  `"$player"`, `"POwns"`, `"ParamEquals"` видны).

Правка: имя от карты сохраняется, `$PLAYER` ставится только если объект
безымянный. Флаг отката `RIDDICK_PLAYERNAME=0`, зонд `[PLAYERNAME]`
печатает, какое имя было и что выбрано.

### Оговорка

Если карта не даёт игроку имени вовсе, а контент всё равно линкует на
`Riddick`, правка не поможет — тогда имя придётся задавать явно. Зонд
`[PLAYERNAME] mapName='...'` отвечает на это одной строкой.

```
[56.60, Char 2559, $PLAYER], PlayDialogue_Hash: 0B877D37  (result: 1)!
[CHOICES] char obj=380 nChoices=0 dlgTick=1698
```

То есть механизм цел от начала до конца: линк с целью `Player` наполняет
`m_liDialogueChoice`, клиент показывает два варианта, нажатие «использовать»
приходит как `param=-1` (выбор реплики), игрок произносит выбранную реплику,
список очищается. Совпадает с наблюдением: «разговор один раз начался».

### Что осталось

Линки с целью **по имени** (`Riddick:99`) по-прежнему не резолвятся, и
правка §30 оказалась холостой:

```
[PLAYERNAME] obj=2559 playerNr=0 mapName='' keep=1 -> $PLAYER
LinkTarget: 'Riddick' -> iTarget=0 items='99'
```

Карта имени игроку **не даёт вовсе**, так что «сохранить имя карты» нечего
было сохранять. Правка при этом не вредна (безымянному объекту `$PLAYER`
ставится как раньше) и остаётся.

Сверка с ретейлом: он резолвит цель тем же `Selection_GetSingleTarget` и
других веток не имеет — ветки `$this`, `$phone`, иначе имя
(`GameClasses_Win32_x86_dll_decomp.c:477592-477605`). Фолбэка нет. Значит в
ретейле игрок это имя носит, и вопрос ровно один: откуда оно берётся.
Единственный оставшийся кандидат — имя шаблона; зонд теперь его печатает
(`[PLAYERNAME] template=`, плюс строка `unresolved: player obj= name=
template=` в момент неудачного линка).

### Временный флаг

`RIDDICK_DLGLINK_PLAYERFALLBACK=1` (по умолчанию **выключен**) отправляет
нерезолвящийся линк игроку. В ретейле такого фолбэка нет, это не правка, а
способ за один прогон проверить, что дальше по цепочке всё цело: если с ним
разговор доходит до конца, единственная поломка — имя.

### Побочно: качание 3PI-режима

В логе видно, как режим прыгает `mode=2 -> 0 -> 2 -> 0` подряд, а
`bHaveChoices` мигает 1/0. Это и есть «камера не перестаёт двигаться».
Разбирать после того, как закроется имя: пока список выборов то появляется,
то исчезает, вход и выход из 3PI будут дёргаться по построению.

## §32. Фолбэк сработал, но выбор всё равно выброшен: гейт 3PI

**Прогон 24** (`RIDDICK_DLGLINK_PLAYERFALLBACK=1`).

### Имя игрока — не из шаблона

```
[PLAYERNAME] obj=2559 playerNr=0 mapName='' template='player_pa1_prisonarea' -> $PLAYER
unresolved: player obj=2559 name='$PLAYER' template='player_pa1_prisonarea'
```

Шаблон называется `player_pa1_prisonarea`, а не `Riddick`. Версия «имя
берётся из шаблона» закрыта. Откуда ретейл берёт `Riddick`, пока неизвестно.

### Фолбэк довёл сообщение, но его выбросили дальше

```
LinkTarget: 'Riddick' -> iTarget=0 ... fallback: routing link to player obj=2559
[29.33, Char 2559, $PLAYER], SetDialogueChoices: '99' parsed=1 iPlayer=0 3PIMode=0 sender=74 owner=2559
```

Выбор дошёл до игрока и разобрался (`parsed=1`), но **`3PIMode=0`**, поэтому
netmsg на клиент не ушёл: у игрока (`iPlayer != -1`) выборы отправляются
только внутри `if(b3PI)`, иначе функция молча возвращает true.

**Сверено с ретейлом** — там ровно тот же гейт.
`FUN_102eb160` (`Char_SetDialogueChoices`,
`GameClasses_Win32_x86_dll_decomp.c:476410-476500`):

```c
if ((*(short *)(iVar2 + 0x2d16) == -1) && list && len > 0) {   // m_iPlayer == -1
    PlayDialogue_Hash(list[0], 2, ...);                        // NPC говорит сразу
    SetLen(0); return 1;
} else {
    if (!list || len < 1) return 0;
    if ((*(byte *)(iVar2 + 0x2074) & 3) != 0) { CNetMsg(0x27); ... }   // 3PI-маска
}
```

То есть дефект не здесь: недостающее звено **выше** — игрок должен уже быть
в 3PI-режиме к моменту, когда реплика NPC закончилась и сработал линк.

Вход в 3PI (`Char_UpdateThirdPersonInteractive`,
`WObj_CharMechanics.cpp:9489-9498`) требует
`(bHaveChoices && m_Go3rdpOnTick) || bSpeaking`, где `bSpeaking` — это флаг
`PLAYER_CLIENTFLAGS_PLAYERSPEAK` **у игрока**. При approach-реплике с
`bIsPlayer=1` говорит NPC, игрок молчит и выборов ещё нет — ни одно из двух
условий не выполняется. У SHABBY разговор пошёл потому, что там линк имел
цель `Player`, и выборы легли на NPC (ветка с ранним `return`), а не
пересылались игроку.

Следующий шаг — найти, что в ретейле включает 3PI (или ставит
`PLAYERSPEAK`) при реплике NPC, адресованной игроку.
