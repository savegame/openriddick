# Отчёт: раздельное отключение эффектов рендера (штатными средствами движка)

Ответ на спеку `Docs/Research_RenderToggles.md`. Дата: 2026-08-04, ветка
`riddick-render`. Связанные доки: `Research_LightPass_Report.md`,
`Research_Lightmap_Report.md`, `Render_Strategy.md`, `HacksAndHooks.md`.

**Главный вывод.** Пользователь был прав: у движка есть штатный,
довольно полный набор переключателей проходов освещения, и он живёт не в
реестре, а в **консольных функциях** — прежде всего в битовой маске
`xr_debugflags`. Ими можно по отдельности выключить: динамический
per-pixel свет, лайтмапный проход, стенсильные тени (везде, а не только
на персонажах), а также включить визуализацию лайтмап-страниц, теневых
объёмов и **тангент-базиса**. Ничего из этого наши env-флаги не
дублируют правильно, и ничего из этого раньше не было доступно из порта —
консольных функций у нас просто некому было выполнить (см. §7).

## Q1. Проходы кадра, в порядке исполнения

Порядок задаёт `m_Priority` вершинного буфера (сортировка в
`CXR_VBManager`), значения — `XRVBPrior.h:44-70` (не-PS2 ветка):

| Приоритет | Проход | Кто ставит в очередь |
|---|---|---|
| −20 `UNIFIED_ZBUFFER` | Z(+стенсиль)-препасс. Пишет `stencil=128` (`REPLACE`, маска 255) | `CXR_Model_BSP2::m_RenderZBuffer` (`WBSP2Model.cpp:327-329`), `CXR_Model_TriMesh::ms_RenderZBuffer` (`WTriMesh.cpp:394-396`) |
| −10 `BACKDROP` | небо/бэкдроп | `Engine_RVC_RenderSky` |
| −5 `FOGPORTAL`, −4 `DYNLIGHT_TEXZFILL` | порталы тумана, z-fill под динсвет | BSP2 |
| −3 `LIGHTMAP` | **лайтмапный проход** (`RenderShading_LightFieldMapping`, программа `XRShader_FP20_LFM`) | `VB_RenderQueues`, `WBSP2Model.cpp:2461-2484` |
| −2/−1 `DYNLIGHTFIRST`/`DYNLIGHT` | **по одному проходу на источник света** (`RenderShading` → `_NDS`/`_NDSP`/`_NDSEATP`), плюс теневые объёмы в стенсиль перед ними | `WBSP2Model.cpp:3415-3429` (BSP2), `WTriMesh.cpp:2270` (модели), `WBSP2Light.cpp:1684+` (динамический свет + тени) |
| 7 `WALLMARK`, 8 `DEPTHFOG`, 9 `POSTDYNLIGHT`, 11 `VOLUMETRICFOG` | декали, depth-fog (texgen-рамп, `Render_Strategy.md` §1), объёмный туман | BSP2 / `CXR_Fog` |
| 2048 / 2063 | непрозрачные / прозрачные модели | TriMesh, Multi |
| 9999 / 10000 / 10100 | флары / UI / курсор | `CRC_Util2D` |
| — | постпроцесс (glow, экспозиция, motion blur, final) | `CXR_Engine::Engine_PostProcess`, `XREngine.cpp:4475+` |

Включается проход тем, что соответствующий `RenderShading*` вообще
вызывается, а внутри — тем, что `m_ShaderMode` попал в `switch` (см. Q6).

## Q2. Где решается «рисовать ли стенсильную тень»

Цепочка (BSP2, динамический источник) — `WBSP2Light.cpp:1695-1700`:

```
int ColorWriteDisable = (m_DebugFlags & M_Bit(12)) ? 0 : CRC_FLAGS_COLORWRITE;
int bShadows =
    !(pL->m_Flags & CXR_LIGHT_NOSHADOWS) &&
    !(_pRenderParams->m_RenderInfo.m_Flags & CXR_RENDERINFO_NOSHADOWVOLUMES) &&
    !(_pRenderParams->m_pCurrentEngine->m_DebugFlags & M_Bit(13));
int bSolidShadowVolumes = (m_DebugFlags & M_Bit(17));
```

То есть **три независимых уровня**: флаг самого источника
(`CXR_LIGHT_NOSHADOWS`), флаг кадра (`CXR_RENDERINFO_NOSHADOWVOLUMES`) и
глобальный дебаг-бит 13. Ровно тот же бит 13 проверяют статические тени
BSP2 (`WBSP2Model.cpp:4429`), персонажи (`WModel_MultiTriMesh.cpp:442`) и
пропсы (`WTriMesh.cpp:2143, 5093, 6077`) — **это единственная точка,
гасящая тени во всём движке сразу**, и она отвечает на вопрос из
`Handoff_Render_Lighting.md` §6.4, почему наш `RIDDICK_SKIP_SHADOWVOL`
задевал только персонажей: он стоял в бэкенде на отборе геометрии, а не
здесь.

Что происходит с остальными проходами. Стенсиль-схема: препасс кладёт
128, объёмы делают INC/DEC вокруг 128 (`WBSP2Model.cpp:111-137`,
`WBSP2Light.cpp:1952-1969`), а шейдинговые проходы рисуются с
`CRC_FLAGS_STENCIL` и сравнением на равенство опорному значению
(`XRShader_FP20.cpp:194`, `:567`). Если объёмы не рисовать, стенсиль
остаётся равным опорному везде → **все шейдинговые проходы проходят
тест, сцена становится полностью освещённой** (не чёрной). Это
безопасное направление: бит 13 не может «залить всё чёрным».

Обратная операция (подавить только запись в стенсиль, оставив объёмы) —
хуже: объёмы рисуются, `ColorWriteDisable` включён только при бите 12, и
без записи в стенсиль они становятся просто геометрией.

**Замеченный дефект движка (не наш):** в дельта-ветке
`XRShader_FP20.cpp:274-279` условие инвертировано относительно свежей
ветки `:194` — при `XR_SHADERFLAGS_NOSTENCILTEST` она делает
`Attrib_Enable(CRC_FLAGS_STENCIL)`, а не `Disable`. Тот же код в
`XRShader_FP20Def_LightField.cpp:181-186` закомментирован целиком. На
поведение влияет только при смене флага между соседними атрибутами;
записан здесь, чтобы не искать заново.

## Q3. Лайтмапы: отдельный проход, и штатный режим «только лайтмап» есть

Лайтмап — **отдельный проход** приоритета `CXR_VBPRIORITY_LIGHTMAP`,
своей программой `XRShader_FP20_LFM`; выбор — `WBSP2Model.cpp:2445-2487`
(ветка `else`, когда не LightField): очередь бьётся на батчи по
`m_iLMTexture`, на батч создаётся `CXR_ShaderParams_LightFieldMapping`
c четырьмя страницами атласа (`m_lLMTextureIDs[iLMTexture*4]`), и
вызывается `RenderShading_LightFieldMapping`.

Штатный путь «только лайтмап без динамики» **существует** и делается
не через caps, а двумя дебаг-битами:

* **бит 19** — не вызывать `RenderShading` (весь per-light проход):
  `WBSP2Model.cpp:3415, 3429` (BSP2) и `WTriMesh.cpp:2270` (модели);
* **бит 20** — не вызывать `RenderShading_LightFieldMapping` (лайтмап):
  `WBSP2Model.cpp:2483`.

Отсюда: `xr_debugflags(524288)` = «только лайтмапы»,
`xr_debugflags(1048576)` = «только динамика». Это ровно тот режим, о
котором просил пользователь в `Handoff_Render_Lighting.md` §1.3, и
собственного делать не нужно.

## Q4. Почему лайтмап оказывается на моделях (версия, не вывод)

Полноценно не проверено; фактура такая. Лайтмап-канал у BSP2 приходит
не из вершин, а из параметров программы (`m_lLFMTextureID[0..3]` +
`m_iTexCoordSet`), которые ставит `CXR_VirtualAttributes_*` при смене
атрибутов. Наш бэкенд `CRC_Attributes` применяет **дельтой** от
предыдущего draw'а, и именно в этом месте у нас уже был доказанный
дефект того же класса: пропущенный `Attrib_Update` на cache-пути
оставлял теневым объёмам состояние предыдущего прохода
(`MDisplaySDL2.cpp:5365-5386`, комментарий с «long dark ribbons»).
Модель оружия рисуется TriMesh-путём сразу после BSP2-очереди, поэтому
«золотая рябь лайтмапа на оружии» ложится на ту же гипотезу:
незаменённый текстурный канал/texcoord-set от предыдущего LFM-батча.
Проверяется дёшево — битом 20 (лайтмап-проход не исполняется): если
рябь с оружия уходит, версия подтверждена.

## Q5. Матрица «эффект → место отключения» (главный результат)

Уровни: **К** — консольная функция движка, **Р** — ключ реестра/ENV,
**А** — атрибут рендера, **Г** — отбор геометрии, **C** — caps.

| Эффект | Самая узкая штатная точка | Ур. | Что остаётся на экране |
|---|---|---|---|
| Стенсильные тени (ВСЕ: BSP2 стат./дин., персонажи, пропсы) | `xr_debugflags(8192)` — бит 13 | К | Свет без теней, сцена ярче; чёрного не появляется (Q2) |
| Стенсильные тени, только выключить построение | `XR_STENCILSHADOWS=0` (`XREngine.cpp:1387`) — грубее, в BSP2 свет течёт сквозь стены | Р | — |
| Динамический per-pixel свет (per-light проходы) | `xr_debugflags(524288)` — бит 19 | К | **Только лайтмапы** + ambient |
| Лайтмапный проход (LFM) | `xr_debugflags(1048576)` — бит 20 | К | **Только динамика** |
| Динамические источники целиком (включая построение) | `xr_dlight(0)` / `XR_DLIGHT=0` (`XREngine.cpp:1274, 1373`) | К+Р | Лайтмапы + ambient, дешевле чем бит 19 (свет не собирается) |
| Спекуляр | `xr_specularforcepower(N)` — форс степени во всех FP20 (`XRShader.cpp:82-117`, `XRShader_FP20.cpp:828, 1270`); отдельного «выкл» нет | К | Диффуз+нормаль без блика (при большой степени) |
| Нормал-мапа / per-pixel вместо вершинного | штатного выключателя **нет**; бит 11 подменяет шейдинг выводом самой нормал-текстуры (`XRShader.cpp:1525, 1624, 1670`) | К | Диагностика, не режим качества |

| Постпроцесс (glow/blur/final) | `xr_ppdebugflags(<маска>)` — `XR_PPDEBUGFLAGS_NOGLOW/NOFINAL/NOGAUSS_X/Y` (`XREngine.h:69-76`, `XREngine.cpp:4475-4479`) | К | Кадр без свечения/финального композита |

**Внимание, бит 14 до сегодняшнего дня был нерабочим:** в
`WTriMesh.cpp` цвета выделялись на 6 элементов при записи `nV*6`
(переполнение VB-арены), индексный массив выделялся `nV*6` **байт**
вместо `nV*6` uint16 и вообще не заполнялся. Исправлено в этом же
коммите; без исправления включение бита портило арену.

## Q6. Caps и выбор режима

`CRC_GLES3::Create` (`MDisplaySDL2.cpp:4111-4192`) объявляет
`HWAPI | ARBITRARY_TEXTURE_SIZE | SEPARATESTENCIL`, 2 текстурных юнита;
при `RIDDICK_HWSKIN=1` добавляется `MATRIXPALETTE`, при
`RIDDICK_FP20=1` — `FRAGMENTPROGRAM20` и 8 юнитов/texcoord-сетов, плюс
`XR_SHADERMODE` пиниться в 5 (`XR_SHADERMODE_FRAGMENTPROGRAM20`), иначе
`AUTO` выбрал бы старшим битом дефёрред-режим, которого у нас нет.

Условие движка — `XRShader.cpp:1268`: `FRAGMENTPROGRAM20` **и** ≥8
юнитов **и** ≥8 texcoord-сетов, иначе `ModesAvail = 0` → `m_ShaderMode
= BitScanBwd32(0) = -1` → все `switch(m_ShaderMode)` в `RenderShading*`
без подходящего case. Ветка `TEXENVCOMBINE` закомментирована (`:1259`),
то есть **без FP20 у движка вообще нет живого пути освещения** — это
уже зафиксировано в `Render_Strategy.md` §2 и подтверждается здесь.

Вывод по «управлять качеством через caps»: **не годится как механизм
конфигурируемости**. Caps здесь двоичны — либо весь FP20-конвейер, либо
мёртвая очередь. Снижать качество надо дебаг-битами (Q5), а на caps
остаётся ровно одно осмысленное решение: FP20 включён или нет.

## 7. Как этим пользоваться из порта (то, чего не хватало)

Все команды выше — консольные функции движка
(`CXR_EngineImpl::Register`, `XREngine.cpp:5985-6052`;
`CXR_Shader::Register`, `XRShader.cpp:2295-2304`). В нашем билде они
зарегистрированы: движок создаётся с флагами 0
(`XRApp.cpp:4228` → `AddToConsole()` + `m_Shader.Register()`,
`XREngine.cpp:1346, 1411`). Но **выполнить их было нечем**: экранной
консоли в порте нет, а единственным исполнителем был одноразовый
`m_PendingExecute` (его использует `RIDDICK_AUTOSTART`).

Добавлено в этом коммите (`XRApp.cpp`, только `PLATFORM_LINUX`, всё —
транспорт текста в `CConsole::ExecuteString`, ни одной новой
рендер-семантики):

| Переменная | Что делает |
|---|---|
| `RIDDICK_CONEXEC="cmd1;cmd2"` | один раз, через `RIDDICK_CONEXEC_DELAY` кадров (деф. 30 — как у `RIDDICK_AUTOSTART`, консольным функциям нужен поднятый движок) |
| `RIDDICK_CONSOLE_STDIN=1` | читать команды из stdin каждый кадр (не блокирует; по умолчанию **выключено**: под gdb инферьор делит терминал, и мы бы съедали команды самого gdb) |
| `RIDDICK_CONFILE=<путь>` | исполнять строки, **дописанные** в файл с прошлой проверки (раз в 15 кадров). `echo "xr_debugflags(8192)" >> path` из второго терминала переключает эффект на живой игре |

Пустые строки и комментарии (`#`, `//`) игнорируются, каждая
исполненная строка печатается как `[CONSOLE] ...`. Содержимое
`RIDDICK_CONFILE`, лежавшее в файле до старта, не исполняется (для
стартового набора — `RIDDICK_CONEXEC`); команда исполняется по переводу
строки.

## 8. Сценарий для ближайшего прогона (`pa1_prisonarea`, чёрный пол)

Запуск: `RIDDICK_FP20=1 RIDDICK_CONFILE=/tmp/rid.cmd
RIDDICK_AUTOSTART=1 RIDDICK_STARTMAP=pa1_prisonarea ...`, дойти до
двора, дальше по одной строке в `/tmp/rid.cmd`, снимая скриншот после
каждой:

```
xr_debugflags(524288)     // только лайтмапы: ложится ли запечка на пол
xr_debugflags(1048576)    // только динамика: чёрный ли пол без лайтмапы
xr_debugflags(1024)       // лайтмап-страницы плоскими цветами
xr_debugflags(8192)       // тени выкл -- их ли мы видим чёрными
xr_debugflags(4096)       // наоборот, показать теневые объёмы
xr_debugflags(16384)      // тангент-базис линиями (пропсы/оружие)
xr_debugflags(0)          // всё обратно
```

Это отвечает сразу на три открытых вопроса `Handoff_Render_Lighting.md`:
чёрный пол (лайтмап vs динамика), «чёрные стенсильные тени» (бит 13/12) и
состояние тангент-базиса (бит 14) — **без единой новой заглушки в
бэкенде**.

Ограничение, которое надо знать заранее: бит 14 рисует базис только для
TriMesh (пропсы, оружие). Для BSP2 такого штатного вывода нет — там
наш `RIDDICK_DBG_SHADER=normal` (нормаль как цвет) остаётся
единственным средством.
