# Покрытие: исходники ↔ декомпил (Ghidra, ретейл PC/Dark Athena)

Черновик по `Docs/Research_DecompCoverage.md`. Методика механическая
(скрипты в `Tools/`), без ручного разбора каждого случая — ручной разбор
уместен точечно, там где автоматика дала кандидата без подтверждения.
Числа ниже — **нижняя граница** покрытия (см. §3 «Что это НЕ измеряет»).

Статус: этапы 1–2 выполнены (инвентарь + автосопоставление по якорям
"Класс::Метод"). Этап 3 (крупные неопознанные области, вопрос про `.exe`,
пополнение `Decomp_Map.md`) — см. отдельный раздел ниже, по мере бюджета.

## 1. Методика

### 1.1 Инструменты

* `Tools/decomp_inventory.py source` — сканирует `Source/P5/**/*.{cpp,h}`,
  извлекает определения `Класс::Метод(` из `.cpp` (регэксп на границу
  идентификатора; эвристика, не полноценный парсер C++ — по требованию
  спеки "механически") и строковые литералы вида `"Класс::Метод"` (якоря
  `Error_static`/аналогичных макросов) из всех файлов.
  → `Tools/out/source_methods.tsv`, `Tools/out/source_anchors.tsv`.

* `Tools/decomp_inventory.py decomp` — построчно проходит все 6 декомпилов
  в корне (см. таблицу ниже), находит границы функций `FUN_xxxxxxxx` по
  формату вывода Ghidra в этом дереве (сигнатура в начале строки → пустая
  строка → `{` в начале строки → тело → `}` в начале строки на глубине 0),
  и строковые литералы внутри каждой функции (bisect по границам).
  → `Tools/out/decomp_funcs.tsv`, `Tools/out/decomp_anchors.tsv`.

* `Tools/decomp_match.py` — джойн по точному совпадению строки
  `"Класс::Метод"` между `source_anchors` (только литералы, реально
  совпадающие с каким-то `Класс::Метод` из `source_methods`) и
  `decomp_anchors` (тип `classmethod`). Один и тот же литерал в декомпиле
  может относиться сразу к нескольким источникам (если один и тот же
  `Error_static("Класс::Метод", ...)` физически продублирован в нескольких
  `.cpp` — обычное дело для `MRTC_System_*` под разные платформы).
  → `Tools/out/matched_pairs.tsv`, `coverage_by_module.tsv`, `coverage_by_dll.tsv`.

Скрипты идемпотентны и перезапускаемы; сами результаты (`Tools/out/`) не
коммитятся (см. `.gitignore`), только скрипты.

### 1.2 Почему якорь "Класс::Метод"

Движок имеет сквозной макрос/функцию-обёртку (в декомпиле видна как
общий хелпер вроде `FUN_100200f0`, вызываемый как
`FUN_100200f0(stack, 0, "Класс::Метод", fmt, ...)`), которая передаёт имя
вызывающего метода строкой — это и есть `Error_static`/аналог. Ghidra
инлайнит короткие строковые константы прямо в текст, поэтому такой якорь
даёт **точное, однозначное** сопоставление одной строкой grep — ровно
то, что описано в §2.3 спеки как самый надёжный признак. Проверено вручную
на первых примерах (`MRTC_SystemInfo::Thread_LocalAlloc`,
`CStrData::Create`, `MRTC_CClassRegistry::RemoveClassContainer`) —
совпадение 1:1 с методом, вызывающим `Error_static` с собственным именем.

Ограничение метода: он находит только те методы, которые **вызывают
`Error_static`/`M_TRACEALWAYS`-подобный макрос с собственным именем в
первом строковом аргументе** — это далеко не все методы движка (по
оценке — единицы процентов). Остальные типы якорей (обратимые djb2-хэши
строк, таблицы `MRTC_IMPLEMENT_DYNAMIC`/`RegFunction`, числовые константы
форматов) в этом заходе **не автоматизированы** — не хватило бюджета
инструментов на данной итерации; см. «Не сделано» в конце.

граница уверенно подтверждённого**, не оценка общего покрытия.

### 3.3 Важное наблюдение: общий MCC-рантайм внутри всех DLL

16 совпадений в `RndrGL_dll_decomp.c` (у которого, по условиям спеки, "в
исходниках вообще нет аналога" — это PC-only GL-рендерер) целиком
относятся к базовым MCC-утилитам, а не к рендер-логике:

```
CStrBase::CompareNoCase, CStrData::Create,
MRTC_CClassRegistry::{LoadClassLibrary,RemoveClassContainer,UnloadClassLibrary},
MRTC_ObjectManager::{CreateObject,UnregisterObject},
MRTC_SystemInfo::{OS_FileAsyncRead,OS_FileAsyncWrite,OS_FileGetTime,
  OS_FileSetFileSize,OS_FileSetTime,OS_FileSize,OS_MemSize,Thread_LocalAlloc}
```

Это ожидаемо: `MCC` — статически линкуемая библиотека нижнего уровня,
её код продублирован (в машинном коде, по одной копии на DLL) в
**каждой** из 6 бинарников — `GameClasses.dll`, `GameWorld.dll`,
`MXR.dll`, `MSystem.dll`, `RndrGL.dll`, и в отдельном `MCCDyn` (похоже,
именно "канонической" динамической MCC-библиотеке, на которую остальные
могли ссылаться, либо ещё одной статической копии — не выяснено, что
именно линковалось откуда; см. «Не сделано»). **Практическое следствие:**
при сверке `RndrGL_dll_decomp.c` не удивляться, если там всплывают
`MRTC_*`/`CStr*`-функции — это не признак того, что рендер-логика
идентична PS3-исходнику, только общая база рантайма. Для собственно
GL-рендер-кода (в `RndrGL`) якорь `Класс::Метод` почти не срабатывает —
ожидаемо: у него нет аналога-класса в PS3-исходнике, отсюда и нечему
совпасть, что подтверждает исходную гипотезу спеки.

## 4. Вопрос про `.exe` (§4 спеки)

**Ответ: декомпиляция `.exe` не нужна на данном этапе.** Помимо
рассуждения по составу `Projects/Main/Exe/` (см. ниже), в декомпилах
нашлось прямое подтверждение механизма, которым подсистемы связываются
между собой — и это механизм не exe-специфичный:

```
GameWorld_Win32_x86_dll_decomp.c:32234  GetProcAddress(hModule,"MRTC_DLLAttachProcess")
GameWorld_Win32_x86_dll_decomp.c:32235  GetProcAddress(hModule,"MRTC_DLLDetachProcess")
GameWorld_Win32_x86_dll_decomp.c:32236  GetProcAddress(hModule,"MRTC_GetClassContainer")
```

Тот же паттерн (тот же набор трёх строк-имён) встречается **во всех 6**
декомпилов — то есть это код `MRTC_CClassRegistry::LoadClassLibrary`
(MCC-уровень, статически слинкован в каждую DLL, см. §3.3), и **любая**
DLL умеет динамически подгрузить любую другую как "class library" через
`LoadLibrary` + эти три экспорта. Значит цепочка инициализации подсистем
каскадом разворачивается уже **внутри DLL**, а не в exe — exe в этой
схеме нужен только чтобы дать первый толчок (загрузить самый первый
модуль и вызвать точку входа). Это соответствует наблюдению из
`AGENTS.md`/спеки: все расхождения этой сессии (`vid_pixelaspect`,
`VIDEO_*`, caps) закрывались сверкой с `MSystem_dll_decomp.c` /
`RndrGL_dll_decomp.c` / `GameClasses_dll_decomp.c` — то есть искомый код
физически лежит в DLL.

Дополнительно: `GetProcAddress`/`LoadLibrary`/`DllMain` встречаются
буквально одинаковым числом раз (33/4/7 или близко) во всех 6 файлах —
кроме `RndrGL`, где `GetProcAddress` встречается 256 раз (в 7+ раз
больше) — это отдельно объясняется тем, что рендер-бэкенд на PC сам
динамически резолвит **сотни** GL/WGL-функций через `wglGetProcAddress`-
подобный механизм (расширения OpenGL), что не имеет отношения к
межмодульной архитектуре.

Обоснование по доступным данным (дополнительно к вышесказанному):

* Все 6 декомпилов — это именно DLL (`*.dll_decomp.c`), а не EXE; в дереве
  `Projects/Main/Exe/` — 373 метода уровня инициализации/точки входа
  (`XRApp.cpp`, `WGameContextMain.*`). Если предположить, что exe в
  ретейле тонкий (просто грузит `GameWorld.dll`/`MXR.dll` и зовёт
  `WinMain`-эквивалент, как типично для этой линейки движков — GameCube/
  Xbox-сборки того же движка используют аналогичную схему "exe = загрузчик
  + `DoModal`"), то основная логика инициализации подсистем должна быть
  видна **со стороны вызовов из DLL в DLL**, а не только из EXE.
* Точную проверку "какие точки входа DLL вызываются только извне и не
  вызываются ни одной из 5 других DLL" **эта итерация не произвела** —
  для этого нужен полный граф вызовов `FUN_xxxx → FUN_yyyy` по всем 6
  файлам плюс список экспортов каждой DLL (не факт, что виден в
  `*_decomp.c` — обычно Ghidra decompile выгружается без таблицы
  экспортов, если её отдельно не запросили). Это следующий шаг, если
  вопрос станет практически важным — см. «Не сделано».
* Практический аргумент против декомпиляции `.exe` сейчас: все известные
  расхождения этой сессии (`vid_pixelaspect`, `VIDEO_*`, caps — упомянуты
  в спеке) до сих пор успешно закрывались сверкой с `MSystem_dll_decomp.c`/
  `RndrGL_dll_decomp.c`, то есть **инициализация рендера физически лежит
  в DLL**, а не в exe (характерно для этого движка — `XRApp.cpp` у нас в
  исходнике дергает `CRenderContext`/`CDisplayContext` через фабрики,
  которые резолвятся в `MSystem.dll`). Это косвенно подтверждает гипотезу
  "exe тонкий".

**Рекомендация:** не декомпилировать `.exe` сейчас; вернуться к вопросу,
если конкретное расхождение упрётся в код, которого нет ни в одной из 6
DLL (тогда у нас будет конкретный `FUN_` или конкретная строка-якорь,
которую можно поискать в остальных пяти файлах первым делом — и только
если не найдётся нигде, разumно подозревать exe).

## 5. Расхождения между исходником и декомпилом

Семантических расхождений в теле функций в рамках этого (автоматического,
по якорям "Класс::Метод") прохода не искали — сопоставление 1:1 по
точному тексту литерала не вскрывает семантику тела функции, только сам
факт совпадения имени метода. Для поиска таких расхождений нужен ручной
построчный разбор конкретных пар (как в существующих записях
`Decomp_Map.md`, например раздел `CXRAG2_AnimLayer` с расхождением
дефолта `m_iMergeOperator`) — это за рамками текущего бюджета инструментов.

Но одно структурное расхождение (не в логике функции, а в **организации
кода**) найдено и стоит записать:

* **Границы DLL в ретейле не совпадают с границами директорий нашего
  PS3-снапшота.** Пример: строки `GUI\VIDSEL\PIXELASPECT`/
  `VIDEO_DISPLAY_WIDTH` — у нас это `Projects/Main/Exe/XRApp.cpp:6375`
  (модуль `Exe`) и `Projects/Main/GameWorld/WFrontEndMod_Menus.cpp:1570`
  (модуль `GameWorld`) — но в декомпиле соответствующий код (по составу
  строк-якорей, см. §3.4) обнаружен в `GameClasses_Win32_x86_dll_decomp.c`
  (бакет с `FUN_104bb830`), т.е. похоже скомпилирован в `GameClasses.dll`.
  **Это догадка** (сверки конкретной функции построчно не делали, только
  совпадение набора строк-якорей в одном адресном кластере) — но если
  подтвердится, означает, что при поиске "где в декомпиле искать логику
  файла X" нельзя полагаться на имя декомпила, совпадающее с текущим
  директорным модулем исходника — нужно грепать по строкам сразу во всех
  6 файлах, что скрипты этого этапа и делают.

## 6. Что не сделано (честно, по бюджету инструментов)

* **Обратимый перебор djb2-хэшей строк** (`CStrBase::StrHash`,
  `MRTC_StrBase.cpp:1614`) — упомянут в спеке §2.3 как рабочий приём, не
  реализован в этой итерации (нужен словарь кандидатных строк + перебор,
  отдельный скрипт).
* **`MRTC_IMPLEMENT_DYNAMIC`/`RegFunction("xr_...")`-якоря** — не
  автоматизированы; дали бы блоковое опознание (регистрация класса/
  консольной команды один раз, а не по одному методу).
* **Полный граф вызовов `FUN_ → FUN_`** (обратный — "кто вызывает эту
  функцию" — по всем 6 файлам разом, с явным списком "вызывается только
  извне DLL") не построен. Ответ на вопрос про `.exe` (§4) дан по более
  дешёвой косвенной улике (`GetProcAddress("MRTC_DLLAttachProcess"/
  "MRTC_DLLDetachProcess"/"MRTC_GetClassContainer")` — универсальный
  межмодульный загрузчик, одинаковый во всех 6 DLL) — этого достаточно
  для практического вывода, но не является строгим доказательством
  "в exe нет уникальной логики".
* Список крупных неопознанных областей (§3.4) — сделан не исчерпывающе:
  только топ-6 самых "густых" по generic-якорям бакетов из 20×6=120;
  остальные 114 бакетов не просмотрены даже агрегатно.
* Пополнение `Docs/Decomp_Map.md` подтверждёнными парами из
  `matched_pairs.tsv` — добавлены 11 однозначных пар (см. файл), из 193
  распознанных методом; остальные либо неоднозначны (литерал совпадает
  с несколькими файлами исходника — типично для `MRTC_System_*.cpp`,
  которые дублируют один и тот же `Error_static`-текст под разные
  платформы), либо просто не перенесены из-за бюджета.
* Инвентарь методов **из заголовков** (`.h`, объявления без определения) —
  собраны только определения из `.cpp`; чисто-виртуальные/inline-в-классе
  методы в текущий `source_methods.tsv` не попадают (у них по построению
  нет отдельного адреса в декомпиле, так что для целей сопоставления это
  не критично, но для полноты «инвентаря классов» стоит отметить как
  пробел).
