## 1. Конвейер поз: где именно IK вклинивается

Всё происходит в одной функции — `CWO_Character_ClientData::OnGetAnimState`
(имя опознано по `Error_static("OnGetAnimState", "Too many layers...")`,
`WObj_CharAnim.cpp:1532`, и подтверждено в декомпиле, см. §3). Порядок:

   WObj_CharAnim.cpp:1537  →  XRSkeleton.cpp:2514 (CXR_Skeleton::EvalAnim)

   и m_pBoneLocalPos[]/m_pTracksRot[] (локальные) для каждого узла, чей rotSlot
   покрыт хотя бы одним слоем. Это единственное место, где скелет целиком
   получает "сырую" анимацию.

2. GATE (WObj_CharAnim.cpp:1580-1586) — большое условие:

   Т.е. если гейт ложный — НИЧЕГО из перечисленного ниже не выполняется:
   ни аим-ОК, ни ОК ног/рук, ни лицевая система, ни коррекция камеры.

## 2. Что трогает IK и при каких условиях

`CIKSystem::DoDualHandIK` (`CIKSystem.cpp:1290-1616`) — единый 2-звенный
аналитический решатель (закон косинусов через
`GetCircleCircleIntersectionPoints`, `CIKSystem.cpp:1618`), используется и
для рук, и для ног (`m_iIKMode` переключает набор track'ов,
`CIKSystem.cpp:1303-1364`). Обрабатывает **строго 3 узла за вызов**:
плечо/бедро → локоть/колено → кисть/ступня (+ attach-точка для рук).

Механизм записи (важно для п. 4-5): решатель **перезаписывает**, а не
блендит, локальную позицию кисти/ступни (`m_pBoneLocalPos[HandROTTRACK] =
NewHandMatLocal`, `CIKSystem.cpp:1401,1611`) и сразу пересчитывает мировые
матрицы всей трёхзвенной цепочки через `EvalNode_IK_Special`/`EvalNode`
(`CIKSystem.cpp:1593,1598,1614` → `XRSkeleton.cpp:1432`/`:1263`). После
этого анимационные повороты локтя/колена для ДАННОГО кадра больше не имеют
значения — цепочка выведена из мировых позиций плеча/бедра (взятых из уже
посчитанной EvalAnim-позы) и целевой точки (ступня-на-земле / рука-на-оружии).

Целевая точка для ног **блендится** (`CPostAnimSystem.cpp:2786-2789,
2806-2810`, `m_FeetBlendVal` от 0 до 1, скорость `FEETBLENDSPEED=1.5` →
~0.67 c), но `DoDualHandIK` вызывается **каждый кадр без исключения**, пока
`CheckOKTorRunFeetIK` разрешает (`CPostAnimSystem.cpp:2782,2795-2796,
2804,2817-2818`) — при `m_FeetBlendVal==0` цель вырождается в саму
анимированную позицию стопы (`MoveDir *= 0`), и решатель просто аналитически
пересобирает колено под уже готовую (анимированную) точку стопы.

**Условия, обязательные каждый кадр:**
- флаги отключения из Environment.cfg: `DISABLE_CHAR_PLAYER_IK`,
  `DISABLE_HAND_IK`, `DISABLE_CHAR_DARKLING_IK` — читаются один раз в
  конструкторе `CPostAnimSystem::CPostAnimSystem()` (`CPostAnimSystem.cpp:
  98-103`), по умолчанию 0 (не отключено);
- `pCD->m_Aim_SkeletonType != 0 || pCD->m_ForcedAimingMode != 0` — общий
  гейт (см. §1); `m_Aim_SkeletonType` — не runtime-вычисление, а
  ключ-значение `SKELETONTYPE` из данных уровня/класса персонажа
  (`WObj_CharCreate.cpp:1517-1523`), значения 0..4
  (`WObj_Char.h:697-701`, 0 = `SKELETONTYPE_NONE`, обычные гуманоиды — 1);
- `CheckOKTorRunFeetIK` (`CPostAnimSystem.cpp:2081-2192`): исключает игрока
  для `FEET_TYPE_HUMAN_BIPED` (см. выше), AG2-флаги
  `IGNOREFEET`/`BEHAVIORACTIVE`, `PLAYER_PHYSFLAGS_NOANIMPHYS`;
- для рук — наличие предмета в `m_Item0_Model` (иначе ранний выход,
  `CPostAnimSystem.cpp:636-644`).

**Чего IK НЕ трогает:** пальцы кистей (их выставляет не IK, а поза захвата
оружия в `EvalHandsOnWeapon`, и то только при наличии оружия), лицевые
track'и/челюсть (отдельная система `CFacialSetup`, §1e), `SPINE2`,
камерные track'и (24, 27, 29).

## 4. Вердикт по гипотезе владельца

**Гипотеза («дефект — именно в костях, которые обрабатывает IK»)
СКОРЕЕ ОПРОВЕРГАЕТСЯ имеющимися данными, с оговорками.**

Обоснование:

1. Список реально замороженных костей из `port_status.md`
   (`frozenLocal=[15 20 27..52]`) **не пересекается** с костями, которые
   трогает IK: ноги (`RLEG/RKNEE/RFOOT/LLEG/LKNEE/LFOOT` = 2..7), руки
   (`RARM/RELBOW/RHAND` = 13/14/16, `LARM/LELBOW/LHAND` = 18/19/21) — их в
   списке нет вовсе. Зато список ровно накрывает:
   - `15` = `SPINE2` — трек, судя по прежним замерам (`Research_BoneAnimation.md`,
     "ПОПРАВКА: совпадение слотов и костей было ложным"), просто не покрыт
     ни одной анимацией/слоем — не про IK и не про баг порта;
   - `20` = `JAW` и, вероятно, `27..37` (кроме именованных `CAMERA_PRIMARY`=27,
     `CAMERA_SECONDARY`=29) — это ровно область, которую пишет **лицевая
     система** (`CFacialSetup::Eval`, §1e), НЕ IK;
   - `38..52` = все 15 track'ов пальцев ПРАВОЙ кисти (`RHAND_THUMB_1` …
     `RHAND_PINKY_3`) — их пишет `EvalHandsOnWeapon`, и только если в руке
     оружие (`CPostAnimSystem.cpp:636-644`); для безоружного персонажа это
     ожидаемое поведение самого движка, а не поломка порта.
   Т.е. **сам список "замороженных" костей объясняется не IK, а либо
   отсутствующей лицевой анимацией, либо отсутствием оружия в руке, либо
   отсутствием анимационных данных на конкретном track'е** — во всех трёх
   случаях IK как система ни при чём.

2. Важная оговорка: `frozenLocal` в `port_status.md` — измерение из
   **другого** расследования ("активные действия замирают, NPC не
   атакует", дата 2026-07-31/08-03), не из свежего прогона по симптому
   именно ходьбы, который описывает текущая задача. Возможно, для симптома
   "ходьба" список другой — это нужно перемерить (см. §6).

3. Отдельно подтверждено **чтением исходника** (не догадка): ОК ног для
   ИГРОКА отключена явно и целенаправленно (`CPostAnimSystem.cpp:2116`,
   `"don't do for the player (right now anyways)"`). Если симптом
   «ноги живут через IK» пользователь наблюдал именно на игроке (Риддике),
   а не на NPC — это **физически не может быть `CIKSystem`**, там код на
   это заведомо не заходит. Для NPC (`m_iPlayer == -1`) ОК ног работает
   штатно.

## 5. Встречная версия («IK — единственное, что двигает эти кости»)

**Частично подтверждается, и это лучше объясняет наблюдение пользователя,
чем прямая гипотеза «IK ломает кости».**

Механизм (см. §2, блендинг цели): `EvalFeetIK` вызывает `DoDualHandIK`
**каждый кадр без исключения**, пока не выполнены отключающие условия. Даже
когда "блок ОК ног ещё не разогрелся" (`m_FeetBlendVal` близко к 0), решатель
всё равно запускается — просто целится в саму анимированную точку стопы.
Решатель — АНАЛИТИЧЕСКИЙ 2-звенный IK (закон косинусов): чтобы посчитать
корректный изгиб колена, ему достаточно знать мировое положение таза/бедра
(берётся из уже посчитанной `EvalAnim`-позы) и мировую целевую точку стопы
(анимированную ИЛИ найденную коллизией с полом). **Само по себе колено не
нуждается в собственном анимационном треке** — оно вычисляется геометрически
из этих двух точек.

Из этого следует правдоподобный сценарий: если корневая анимация
(root-motion, движение таза) у NPC продолжает отрабатывать (перемещение
персонажа по уровню не встало), а именно КОЛЕННЫЕ/ГОЛЕНОСТОПНЫЕ повороты в
конкретном анимслое почему-то не приходят (то самое "первый кадр шага и
скольжение" из `Research_BoneAnimation.md`), то нога всё равно будет
выглядеть шагающей — потому что её финальную позу считает не анимация, а
IK, отталкиваясь от движущегося таза и (либо анимированной, либо
физически найденной) точки стопы. Итог: **визуально нога "живёт" не
потому что IK "чинит" анимацию, а потому что для этой конкретной кости
IK и есть основной источник финальной позы почти всегда, когда персонаж
не игрок** — совпадает с наблюдением пользователя, но переворачивает его
трактовку: это не признак "здоровья" IK как индикатора, а нормальная
архитектура движка (колено почти всегда IK-driven у NPC).

Вывод по встречной версии: **скорее да, чем нет** — но это не противоречит
и не подтверждает исходную гипотезу о "поломке" IK, а скорее показывает,
что наблюдение пользователя (нога шевелится) ничего не говорит о здоровье
IK-подсистемы как таковой — она всегда так работает.

## 6. Что мерить следующим прогоном

Чтобы один прогон развёл оставшиеся версии, нужны зонды, привязанные не к
абстрактным "костям", а к конкретным веткам этого файла:

1. **Гейт §1 (WObj_CharAnim.cpp:1586) на проблемном персонаже.** Одна строка
   на первый кадр каждого нового AG2-состояния:
   `[OK-GATE] obj=<id> isPlayer=<m_iPlayer!=-1> aimSkelType=<m_Aim_SkeletonType> forcedAim=<m_ForcedAimingMode> controlMode=<Char_ControlMode> gate=<bool>`.
   Даёт однозначный ответ, доходит ли конкретный NPC/игрок до IK-блока
   вообще в момент "сломанной ходьбы".

2. **CheckOKTorRunFeetIK (CPostAnimSystem.cpp:2081) — причина возврата
   false**, если она есть: `[FEETIK-GATE] obj=<id> playerExcl=<bool>
   ignoreFeetAG2=<bool> behaviorActive=<bool> noAnimPhys=<bool>
   feetBlend=<val> frontFeetBlend=<val> result=<bool>`. Печатать РОВНО
   там, где сейчас пять условий на строках 2115-2118 и 2185.

3. **Факт входа в лицевую систему** (WObj_CharAnim.cpp:1754):
   `[FACIAL] obj=<id> pFacialSetupNULL=<bool> iFacialSetup=<val>
   nBoneTransform=<val> vs LEYE=90`. Если `pFacialSetup` систематически
   `NULL` — это отдельный, не-IK дефект (ресурс `CFacialSetup` не
   резолвится), и он ОДИН объясняет кость 20 и, вероятно, 30-37 из
   `frozenLocal`.

4. **Факт входа в EvalHandsOnWeapon дальше раннего выхода**
   (CPostAnimSystem.cpp:643): `[HANDWPN] obj=<id> hasWeaponModel=<bool>
   holdType=<enum>`. Если `hasWeaponModel=false` у персонажа из
   `frozenLocal`-замера — пальцы 38-52 объяснены штатным поведением, не
   багом.

5. **Свежий `frozenLocal` именно на симптоме ходьбы**, а не на старом
   "NPC не атакует": тот же зонд `RIDDICK_DBG_BONES`, что уже есть
   (`WTriMesh.cpp`, см. `Docs/HacksAndHooks.md`), но снятый на кадре,
