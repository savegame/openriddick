## 1. Что уже точно известно

Оружие не рисуется ни в руках игрока, ни у NPC. При этом стрельба работает,
модели оружия **не** числятся отсутствующими (в логах нет ни одного варнинга
про `Weapons/*.XMD`, кроме двух фронтендовых `gun_1911_02` и `Ass_Automatic`,
которые к геймплею отношения не имеют).

Зонд `RIDDICK_DBG_ITEM=1` (`WObj_CharRender.cpp`, перед гейтом рендера
предметов) в прогоне `i1_pigsville` даёт:

```
[ITEM] obj=2559 local=1 i0{model=0 flags=0x8  equipped=1 norender=0 rotTrack=0  attach=0} ... nBones=120
[ITEM] obj=101  local=0 i0{model=0 flags=0x2d equipped=1 norender=0 rotTrack=22 attach=6} ... nBones=70
[ITEM] render FAILED (GetResource_Model returned NULL): iModel=0 rotTrack=0 nBones=120
```

Отсюда следует:

* `equipped=1` — `RPG_ITEM_FLAGS_EQUIPPED` выставляется и реплицируется;
* `norender=0`, `noitemrender=0` — запрещающие флаги не при чём;
* `rotTrack=22`, `attach=6` у NPC — ключи `ATTACHROTTRACK` и `ATTACHPOINT`
  из данных предмета **прочитаны и доехали до клиента**;
* `model=0` — и только он. То есть срабатывает первый же ранний выход в
  `CAutoVar_AttachModel::GetModel0_RenderInfo`.

Единственная точка присваивания:

```cpp
// Source/P5/Projects/Main/GameClasses/WRPG/WRPGItem.cpp:352-356
case MHASH2('MODE','L'): // "MODEL"
    {
        m_Model.m_iModel[0] = m_pWServer->GetMapData()->GetResourceIndex_Model(KeyValue);
        break;
    }
```

Соседние `case`'ы того же `switch` (`ATTACHROTTRACK` строка 379,
`ATTACHPOINT` строка 385) отрабатывают — значит сам разбор ключей и хеш-
диспетчеризация исправны.

Дальше цепочка: `GetResourceIndex_Model` (`WMapData.cpp:500-546`) для имени
без `.XW` и без известного кастом-класса сводится к

```cpp
return GetResourceIndex(CFStrF("%s:%s", m_spWData->GetResourceClassPrefix(WRESOURCE_CLASS_MODEL_XMD), _pName),
                        WRESOURCE_CLASS_MODEL_XMD);
```

Проверено и исключено, прогон не нужен: `MAUTOSTRIP` в нашей сборке
раскрывается в пустоту — ни `MRTC_AUTOSTRIP`, ни `MRTC_AUTOSTRIPLOGGER` не
определены (`Source/P5/Shared/MCC/MRTC.h:2355-2359`).

## 2. Вопросы

Отвечать с точными `file:line` и короткими цитатами (5–15 строк).

1. **Доходит ли `case MHASH2('MODE','L')` до выполнения вообще?**
   Найти, откуда вызывается этот `OnEvalKey`/`EvalKey` для `CRPG_Object_Item`,
   какой объект-реестр ему скармливается, и есть ли ветка, в которой ключ
   `MODEL` у предмета просто отсутствует в PC-данных. Особое внимание:
   закомментированный `case MHASH3('ATTA','CHMO','DEL')` (`WRPGItem.cpp:364-370`)
   и живой путь `ATTACHMODEL<n>` → `m_Model.SetModel(...)` около
   `WRPGItem.cpp:773`. Возможно, PC-контент объявляет модель оружия другим
   ключом.

2. **Что именно возвращает `GetResourceIndex(..., WRESOURCE_CLASS_MODEL_XMD)`
   и при каких условиях 0?** Полный путь `CMapData::GetResourceIndex`:
   ищет ли он в уже построенной таблице ресурсов карты или добавляет по
   требованию; что происходит, если ресурс запрашивается **до** того, как
   таблица ресурсов заполнена (порядок инициализации — предметы создаются на
   сервере при спавне персонажа, возможно раньше загрузки таблицы моделей).

3. **Логирует ли этот путь хоть что-нибудь при неудаче?** Если нет — назвать
   место, куда осмысленно поставить одну строку диагностики, чтобы увидеть
   само имя модели, которое запрашивали. **Имя строки-значения (`KeyValue`) —
   это ключевая недостающая улика.**

4. **Префикс класса.** Что возвращает
   `m_spWData->GetResourceClassPrefix(WRESOURCE_CLASS_MODEL_XMD)` и как
   итоговая строка `"<префикс>:<имя>"` сопоставляется с именами в таблице
   ресурсов карты. Не может ли быть расхождения регистра/разделителя
   (`\` против `/`) именно для этого класса — у нас файловый слой
   регистронезависимый, а вот таблица ресурсов может сравнивать строго.

5. **Сравнение с рабочим случаем.** Найти класс ресурса, который в этом же
   прогоне разрешается успешно (например модель тела персонажа), и показать,
   чем его путь получения индекса отличается от пути модели предмета.

Ответ — до ~120 строк, лучше ссылками, чем прозой. Фиксы не предлагать.
