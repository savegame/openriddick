# Спека на исследование: покрытие исходников декомпилом (и обратно)

Поставлена владельцем 2026-08-04. Задача **исследовательская**: построить
двустороннюю карту «исходник ↔ декомпил» и посчитать покрытие. Правки в
коде по ходу не делать.

Мотивация — накопленный опыт этой сессии: каждый раз, когда мы сверялись
с декомпилом ДО правки, версия либо подтверждалась, либо отменялась за
один заход (кубические проекции, `.a` против `.rgb`, порядок TSLV). А
когда шли от симптома — тратили по прогону на версию. Карта нужна, чтобы
сверка стала дешёвой операцией, а не раскопками.

## 2. Что надо получить

### 2.1 Инвентарь исходников

Список классов и методов по модулям (`MCC`, `MSystem`, `XR`, `XRModels`,
`Classes`, `GameClasses`, `GameWorld`, `Exe`) — имя класса, имя метода,
файл:строка. Механически: по объявлениям в заголовках и по определениям
`Class::Method` в `.cpp`. Порядок величины — десятки тысяч методов, поэтому
инвентарь строится **скриптом**, а не чтением (`Tools/` — подходящее
место, назвать `decomp_inventory.*`).

### 2.2 Инвентарь декомпила

Список `FUN_xxxxxxxx` + их «якоря»: строковые литералы внутри функции,
уникальные константы, характерные последовательности вызовов. Тоже
скриптом.

### 2.3 Сопоставление

Автоматически — по якорям:

* **строковые литералы** — самый надёжный: `Error_static("Method", "...")`,
  `M_TRACEALWAYS`, `ConOut`, имена шейдерных программ, ключи реестра;
* **хэши строк** — `CStrBase::StrHash` это djb2 со свёрткой регистра
  (`MRTC_StrBase.cpp:1614`), поэтому константы в декомпиле **обратимы
  перебором**; приём уже неоднократно сработал (см. `Decomp_Map.md`);
* **имена классов в MRTC_IMPLEMENT_DYNAMIC** и таблицы регистрации
  консольных функций (`RegFunction("xr_...")`) — дают целые блоки сразу;
* **числовые константы формата** (версии чанков, магии, размеры).

Ручной разбор — только там, где автоматика дала кандидата без
подтверждения.

### 2.4 Метрики

1. **Покрытие исходников декомпилом**: сколько методов исходника
   опознано в декомпиле. Разрез по модулям — это важнее общего числа:
   у `RndrGL` в исходниках вообще нет аналога (PS3-снапшот), у
   `GameClasses` должно быть высокое совпадение.
2. **Покрытие декомпила исходниками**: сколько `FUN_` опознано. Остаток —
   самое ценное: это код, которого **нет в нашем снапшоте** (PC-only
   подсистемы, поздние правки Dark Athena, RndrGL целиком).
3. Список «висячих» функций декомпила, сгруппированный по модулю и по
   соседству адресов — с гипотезой, к какой подсистеме относится.

## 4. Вопрос про `.exe`

Оценить, что даст декомпиляция самого исполняемого файла. Аргументы за:
в нашем дереве `Projects/Main/Exe/` — это `XRApp.cpp` (7.7k строк),
`WGameContextMain.cpp`, точка входа и вся инициализация подсистем,
включая выбор рендерера, настройки видео и стартовую последовательность —
ровно те места, где порт уже несколько раз расходился с ретейлом
(`vid_pixelaspect`, `VIDEO_*`, caps). Против: exe скорее всего тонкий, а
вся логика в DLL.

Ответ должен быть обоснован: найти в декомпиле DLL точки, которые
**вызываются извне** и чьих вызывающих нет ни в одной DLL — это и есть
след exe. Если таких мало, декомпиляция не нужна.

## 5. Чего НЕ делать

* Не читать декомпилы целиком — только grep и скрипты (файлы по
  сотни тысяч строк).
* Не править код по ходу: любые найденные расхождения — записывать в
  отчёт, отдельной строкой с `file:line` обеих сторон.
* Не смешивать с текущей задачей по освещению.
